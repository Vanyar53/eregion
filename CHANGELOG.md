## [Unreleased] — toward 0.3, "the full loop runs"

### Changed
- **Decision: the rules fallback does not deny Azure DNS/IMDS, even on a NIC NSG that looks dedicated** (19/10, sixth review S7, last part). Azure only accepts these rules with source `*`, which reaches every NIC on the NSG, now or later; an NSG that looks dedicated at isolation time may not be (L24: a NIC away in quarantine, one attached meanwhile). The quarantine path denies them without that risk; the fallback keeps saying they stay reachable. Recorded in `docs/azure.md`, the ROADMAP and next to the code.
- **claude-sonnet-5-5 is the default model** (19/10, #139): after the harness (36/36, no overconfident error; claude-sonnet-4-6: 32/36, 4) and an end-to-end run on the bench (T1486 → isolate_vm 0.80, T1110.001 → block_suspicious_ip 0.88). One line in `eregion_core/models.py`. Annatar's campaign planner keeps claude-sonnet-4-6 (its own default, `DEFAULT_ANNATAR_MODEL`): claude-sonnet-5-5 declines the red-team planning prompt (`content_filter`, measured the same day) — the planner now says so instead of falling back in silence, and goes through the tool-choice fallback.
- **One definition of the default model** (19/10): it was written in eight places (compose, agent, War Room, four CLI options, Annatar's planner). `eregion_core/models.py` holds it; everything reads `glorfindel_model()` / `annatar_model()`, docker compose passes an empty variable for « default », and `tests/unit/test_models.py` fails on any other model name in the code. The default is still claude-sonnet-4-6; switching is one line after an end-to-end run.
- **The observation's Glorfindel decides with claude-sonnet-5-5** (19/10): in the harness, 36/36 good calls and no overconfident error (claude-sonnet-4-6: 32/36, 4), about three times faster, more cautious on confidence (12 needless holds, harmless in human-only). Switched on the hosted, read-only VM; the code default stays claude-sonnet-4-6 until an end-to-end run.
- Direction set for 1.0 (eighth pass): SOC functions for the cloud workloads of teams without a SOC, proven by attack and by failure. Three-agent loop — Annatar attacks, Gothmog breaks, Glorfindel detects and responds — with Orodruin as the disposable runner and Celebrimbor as the bench builder. Production rule: never a fault or a destructive action on a real workload. README, ROADMAP, `docs/architecture.md` (shared vocabulary, the three zones), session files for Orodruin and Gothmog, reserved folders `gothmog/` and `infra/orodruin/`.

### Fixed
- **The hosted Glorfindel no longer fills its disk** (20/10): each redeploy rebuilt the image and left the old layers in containerd (Docker 29) — 87 % of the 32 GB disk, a full disk would have stopped the watch and broken H0's four-week run. Pruned (back to 12 %); `glorfindel-host-start` now prunes dangling images after the build. `glorfindel-host-status` no longer counts warnings as errors (LiteLLM's missing-botocore notice made 4 false errors a day).
- **A model that refuses a forced tool choice can still decide** (19/10): claude-sonnet-5-5 rejects `tool_choice` naming a tool (« type tool and any are not supported »), so every decision and rule proposal failed before the model saw the signal. `eregion_core/llm_call.py` retries once with `auto` and remembers the model; no tool call then → no decision → escalation (the defensive parse). The default model is called as before.
- **The ransomware rule no longer goes blind after a boot on a 60-s DCR** (#105, measured 19/10): the agent's first upload packs samples under one timestamp, `min(Gap)` read ~0 and forced fine mode for 10 min — on gondolin with a 60-s DCR, 74 and 99 MB/s samples were missed by the rule and seen by the fixed one on the same window. The step now ignores sub-second gaps (`minif(Gap, Gap >= 1s)`); no change on 3 days of benign data. Live, the hosted Glorfindel caught the write only once the batch left the window (07:09). Mutant M62.
- **litellm pinned to 1.86.1** (19/10): the dependency read `litellm>=1.0`; a rebuild picked 1.106.0, which imports an absent `mcp` module on the decision call — the hosted Glorfindel kept detecting but every decision failed (`cycle_failed`). `glorfindel-host-status` now counts the failed decisions of the last 24 h.
- **The bot's sync no longer loops on a failing edit** (19/10): Discord archives an idle thread (an edit there fails, 50083) and a message deleted in Discord is gone (10008) — both were retried every 15 s, 10 800 errors in a day. The thread is reopened for the edit and closed again, a deleted message is forgotten, and any other failure is tried once per state change.
- **Discord follows the War Room** (16/10): the bot only posted new cards — a card acknowledged or judged in the War Room kept live buttons in Discord, and repeats never showed. It now re-reads the cards it posted every 15 s and edits a changed message (a « État » field, buttons greyed once closed, « N× »), and archives a VM's thread once nothing is pending. The VM card's Right / Wrong buttons in the War Room also acknowledge, like the To judge list.
- **Discord buttons work after a restart** (16/10): the bot keeps each card's message id and gives it its view back at startup (cards of the last 14 days); every redeploy left them answering « interaction failed ».
- **`glorfindel audit <name>` finds the VM** (16/10): a name now resolves through the discovered VMs, for every command that takes one (it answered « not found in ? »); two VMs of that name → refused with both ids, never the first.
- **Tests no longer write the operator's discovery cache**: `AssetRegistry()` bound `~/.glorfindel/discovered_assets.json` at import, so the conftest's redirection did nothing (found when a new test wrote fake VMs there, 16/10 — cleaned).
- **The Discord bot no longer says « done » for what did not run** (16/10): the first real card read « IP suspecte bloquée » for a block human_only had held. The title says « Recommandé : … (non exécuté) » for a held decision; the embed carries the model's explanation, the IP:port, the rule and the confidence, then why nothing ran; Right / Wrong / Unsure buttons record the observation's verdict from Discord.
- **What the War Room got wrong once hosted** (16/10): « missing credentials » on a managed identity (the status now comes from what Azure answered); the autonomy mode editable in observe-only (locked to human-only, refused by the API); a « Run scenario » control posting to a route that never existed (removed, with `/api/scenarios`); drag-and-drop slots drawn as empty cards; every escalation in red in the feed (red now means isolate or block); each protected VM counted « unprotected » (the vault names items `VM;iaasvmcontainerv2;<rg>;<vm>`); the quarantine NSG on standby shown « restricted »; long rule names broken over five lines.
- **An empty AZURE_CLIENT_ID no longer hides the managed identity** (H0, measured on the hosted VM): docker compose passes `AZURE_CLIENT_ID=""` (and SECRET, TENANT) when the host has no service principal; azure-identity's `EnvironmentCredential` takes that for set, `ClientSecretCredential("")` raised, and `DefaultAzureCredential` never reached the VM's identity — discovery and posture failed. The CLI now unsets these variables when empty, before any command. Mutant M56.
- **An isolation by rules now says Azure's DNS and IMDS stay reachable** (sixth review, S7): it was in the outcome and shown nowhere. An orange « ⚠ DNS/IMDS » chip next to ISOLATED, a line in `glorfindel list`, a note in the autonomous isolation's notification. And the readiness gate learns of a quarantine swap refused at execution (an Azure Policy its rights read can't see): a `quarantine_refused` reserve, the isolation counted as by rules, until one puts the quarantine on every NIC. Mutants M52, M53.
- **A verification that raised mislabelled an isolation that did happen** (sixth review, S9): the exception left the graph, and the watch's safety net recorded a `cycle_failed` with an empty action and `executed: False` — no Revert button for a VM that was isolated. `verify_action` now treats it as an action that could not be verified: the action and its outcome are kept, and the card is a `verification_failed`, like an unreadable rule list. Mutant M51.
- **The session drain spared every session with a forensic source** (sixth review, S8) — any port, either direction — while the quarantine's allow only lets TCP in on the forensic ports: a session the VM opened towards that host, or one on another port, survived the isolation. The drain now spares only TCP sessions from a forensic source to a forensic port of the VM. The filter was checked with a real `ss`; mutant M50.
- **The account-creation rule (T1136.001) fires on real creations only** (seventh review, P1). It matched every line mentioning useradd: failures (« already exists »), the « new group » line of the same creation, package-manager system accounts. On 14 days of the bench it matched only Azure agents' own accounts. It now keeps « new user: name=… » lines, except a system account without a login shell and the known agent accounts without a shell — a system UID with a shell, or an agent's name with a shell, stays. Validated on the real KQL engine (9 cases; 0 line on 14 days instead of 6); same output columns.
- **The card's NSG group no longer contradicts the readiness gate** (seventh review, P2): « NSG precedence » failed (✗) as soon as an allow came before a Glorfindel deny, while the gate knows the quarantine NSG neutralises it for an isolation and makes it a reserve for a block. The audit now judges it with the gate's own rule (`readiness.isolation_by_quarantine`): ok when the isolation goes through the quarantine, a reserve (⚠) otherwise — never a failure, as in the gate.
- **The War Room's root dot no longer reports a breakdown for a fleet posture** (seventh review, P3): a VM without a usable backup turned it red, « A module is in error ». It is now orange and says how many VMs lack a backup; red stays for a module that actually fails (a rule's poll, the audit itself).
- **The audit read a 0-s cadence right after a boot** and claimed the ransomware rule's fine mode: the agent's first upload sends several samples under one timestamp (measured on the bench). The cadence is now the smallest gap between seconds that each carry one sample; until there is one, the audit says it can't tell yet. Measured: 10 s on the bench, the real cadence.

## [0.2.0] — 2026-10-15

First release to be tagged; earlier work is in the git history.

### Glorfindel — detection and response
- Continuous rule-based detection (RulePoller, one query per rule, rows routed to VMs), assets discovered from their own telemetry (Log Analytics Heartbeat).
- Decision by an LLM (provider-agnostic via LiteLLM) over the enriched signal, a RAG memory of past cycles (ChromaDB) and validated few-shot examples, framed by deterministic guards: executable action, confidence gate, uncharacterized-signal guardrail, attribution, release precondition, autonomy mode, readiness lock. Any model failure escalates; it never acts.
- Autonomy per asset: `human_only` (default) and `non_disruptive`, with a readiness check before a VM leaves `human_only`; observe-only mode on read-only credentials.
- Verified response on Azure: just-in-time isolation by a quarantine NSG (the customer's NSG set aside and restored, compatible with Terraform — measured), Azure DNS and IMDS denied, open sessions cut, every NIC covered, NSG precedence checked, IP blocks in both directions, reassertion every minute, snapshot and restore through Recovery Services Vault with Run Command neutralized before a restore.
- Purple loop: detection rules authored by the LLM, grounded on a technique catalog and the real table schema — reactively on a missed attack, proactively with `propose-rules`; every rule is a proposal a human approves.
- War Room web UI, Discord bot, terminal dashboard; observation kit (`glorfindel verdict`, `glorfindel report`).

### Annatar — attacks
- Scenarios validated in real runs on Azure: T1486, T1041, T1110.001, T1548.003, T1136.001, and T1110 with T1548 in parallel.
- Generative campaigns: a kill chain composed from the shared technique catalog, optionally LLM-planned, within a scope and a budget.

### Proof
- Hermetic unit tests (no Azure call, no LLM call), property-based invariants on an in-memory Azure whose world moves, a mutation check with a control set, cross-process lock tests, a daily azurerm canary, the Celebrimbor bench (Terraform).
