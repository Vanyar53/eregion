### Added
- **The coverage matrix, its evolution and the non-regression, in the console** (C1, #80, 30/10; `docs/glorfindel.md`, « Matrice de couverture »; `docs/architecture.md`, « Le run, unifié »; `docs/design/console.md`).
  - **One run format for an attack and a fault.** Annatar and Gothmog write the same report, `runs/<run_id>.json`, from one class in the shared core (`eregion_core/run_report.RunReport`; each injector keeps only how it prints it). The report now says what it is, in `metrics`: `run_format` (1), `kind` (`technique` or `fault`), `injector`, `experiment_id` (the ATT&CK id or the fault's id). A compatible addition: a report written before reads as before, `schemas/run_report.schema.json` already allows other fields, and the signal contract (`eregion_core/signals.py`) does not change. One reader (`read_run`) gives the view the console shares; `timeline` joins the watch's decision and gives an incident's times — attack, detection, decision, verified action (`outcome.verified_at` when the watch writes it, else the record's time) — the format BL1 measures the time to contain on.
  - **The matrix** (`eregion_console/coverage.py`, `GET /api/coverage[?kind=technique|fault]`): for each technique of the catalog and each declared fault — and a run outside the catalog, said so — its last run (date, detected or not, time to detect, Glorfindel's decision, time to contain when an isolation or a block was executed and verified), its last proof (a technique detected **and** with its decision attached; a fault PASS with the watch running), its last ten outcomes and its state: `proven` (under 21 days), `aging` (21 to 30), `stale` (over 30: the alert), `regressed`, `unproven`, `never`. **The evolution**: twelve weeks, the techniques detected in the 30 days before each. Read from every run report the host keeps (campaigns included) and the watch's cycles, over the whole history — never from the cloud, never from the exercise windows (7 days).
  - **The non-regression**: a technique detected before whose last measured run missed (a fault PASS then FAIL) is `regressed`, red, with the run that held and the run that lost; a run that measured nothing (unknown, `--without-glorfindel`, a fault refused) neither proves nor regresses. `eregion coverage [--json] [--check]` prints the matrix from `runs/` and, with `--check`, exits 1 on a regression — after a replay of the catalog on the bench.
  - **In the console**: the right column of Annatar's and Gothmog's pages is the matrix (it replaces the catalog list); on the overview, the coverage says what regressed (red, a link to its page) and the stale proofs, and the age of the last proof is read over the whole history — over 30 days it is said, red, instead of « none in 30 d ».
  - **After the review**: a run dated more than 5 minutes ahead is left out of the matrix and the indicators, and said (a `missed` of 2076 kept a row regressed for ever); the decision attached is the watch's record on the run's VM (Annatar's reports now name it, `metrics.resource_id`), of the run's own technique, the closest to its detection; a fault whose start failed is neutral; the detections are indexed once (bisection), each report read once per file version, the matrix computed again only when a file changes or after 30 s (2 000 runs and 40 000 cycles: 0.2 s, 6.4 s before); the overview's time to contain goes through `timeline` too; `eregion coverage` prints no control character; `schemas/run_report.schema.json` declares the new fields.
  - Tests `tests/unit/test_coverage.py` (fake runs replayed), `tests/unit/test_run_report.py` (the core alone), the injectors' (`-k unified`); mutants M1800–M1829, M1880–M1889 (M560 retargeted on the indexed search).

### Fixed
- **The orphan sweep no longer opens a VM that took a deleted VM's address** (I5Q, #327, 29/10; `docs/design/preuves.md`, « I5Q »). A VM blocked for itself and then on its subnet — its own rule at 200, the perimeter one at 210 —, that rule turned into an allow by someone, then the VM isolated by rules and deleted, and a new VM given its address and its NSG: the reassertion's orphan sweep took the deleted VM's isolation off the new VM, and the attacker, let through the subnet's NSG by the turned rule, reached it on 22 — the perimeter block standing behind. Found by the machine (seed 101 at 500 sequences, RB1's fourth review), present before RB1. A deny of a NIC that no longer exists now stays when one of our rules turned into an allow, on the same side and aimed at an address it cuts (or at all), sits on an NSG that governs that NIC: the card says which rule and why; once that rule is put back or removed, the next pass takes the deny off. The new VM stays cut off meanwhile — never opened. The release of a deleted VM had the same hole, found by the machine once its new composite rule (`turned_then_address_reused`) made the state common (seed 322 at 500, I4): the denies of its placements, and those I7S looks for on every NSG, are kept the same way — `release_partial`, the turned rule named; a live VM's own turned rule never holds its release. Tests in `tests/unit/test_invariant_regressions.py` and `tests/unit/test_orphan_sweep.py`; mutants M1730–M1747. A deny kept that way no longer loses its card when its sibling (the other direction, cutting the same VM) is taken off: the card they share stayed resolved, the kept deny unsaid (`glorfindel/orphans.py`). A card said before the rule was turned (in `human_only`, or shared with the sibling) no longer keeps telling to delete the deny, which would open the VM: it is replaced by one naming every turned rule the VM's kept denies wait behind, whose first steps put them back as denies. The NSGs that govern the VM cut are read again just before a removal, and the guard played again.
- **A block written again no longer cuts off the VM that took over the old address** (I4A, #328, 29/10; `docs/azure.md`, `docs/design/preuves.md`). Found by RB1's invariant machine (seed 8675), present on main before it. A VM blocked; someone turns one of its block rules into an allow; its IP changes and Azure hands the old address to a new VM, which the turned rule now lets the attacker reach. The block written again (a second `block`, or the reassertion outside `human_only`) rewrote that rule by its name for the VM's new address: the allow was gone, and an operation on one VM changed another VM's flows (I4). Now such a rule is left as it is: an allow of ours aimed at an address that is no longer the NIC's, held by another NIC, or by nobody knows whom (the NICs unreadable, a range), or at any address on an NSG others share; and our own deny on such an address while a rule of the NIC's block turned into an allow waits behind it, on one of the NIC's NSGs — aimed at the address, any, a range holding it, or a tag (moved, it let that allow open the other VM — seed 42 at 2,000; those NSGs unreadable, it is kept). A rule of the first pair that can't be taken off is said (`drop_failed`). The block is written under the NIC's second name (same NIC hash: found by the verification, the unblock, the reset and the orphan sweep), the first pair's other rule taken off once it holds. The block's outcome says what it left (`left_rules`); the reassertion says it once on a card (`rule_left`), and writes nothing. An old address nobody holds: rewritten as before. Tests `tests/unit/test_invariant_regressions.py` (the frozen sequence, no longer `xfail`); the invariant machine draws the sequence (`address_reused_under_a_turned_rule`); mutants M1755–M1769; the isolation's side of the same defect is frozen as a strict `xfail` for I4B (#333). **Still open** (I4B): the unblock and the reset take off a rule with the NIC's hash whatever it has become — the turned allow the block now leaves, too —, so the VM given the old address still loses those flows there; frozen as strict `xfail`s, unseen by the invariant machine (it drops the attacker's flows at unblock and reset).

## [0.4.6] — 2026-10-29 — "held at the source"

### Security
- **The images published, signed and pulled by their digest** (CI3, #267 step 2, 29/10; findings P-02 — no SBOM, no signature — and V-22 — unsigned tags; `docs/operations.md`, « Les images publiées »; the threat model, frontier 6).
  - **The head of every push to `main` publishes its two images** to GHCR, `ghcr.io/vanyar53/eregion-glorfindel` and `-annatar`, tagged `sha-<commit>` (`.github/workflows/publish.yml`). Built as CI1 builds them (plus UID/GID 1000, the hosts' user, and the version and commit as labels), proven in the image **before** the push, then attested — a SLSA provenance (`actions/attest-build-provenance`) and an SPDX SBOM (`actions/attest-sbom`), both pushed next to the image — and signed keyless (cosign, a sigstore certificate on GitHub's OIDC token: no long-lived key, no secret). The workflow then verifies them as H0 does. Every commit, not the release: a draft targets a commit of `main` and H0 deploys it as soon as it is published, so its image must already be there; the CD waits for the commit's `publish (glorfindel)` check like the main CI's. That workflow alone may write a package, mint an OIDC token or write an attestation, at its job's level, on a push to this repository's `main` only — never a pull request, a fork's included (`tests/unit/test_workflows.py`). The images are public: the repository is, and an image holds no secret.
  - **H0 no longer builds** (its CD, `eregion_cd.py`): the release's image digest is read anonymously on the registry (the sha256 of the manifest read: a tag is a hint), then its signature and its provenance are verified by a pinned cosign (v3.1.3, its sha256 checked before each use): the publishing workflow of this repository, on `refs/heads/main`, triggered by a push, **at the tag's commit**; the provenance is read again (subject, workflow, repository, ref, event, source commit, a GitHub-hosted runner). Pulled by that digest, its labels must say the tag and the commit, and it must run as H0's user. An image absent, private, unsigned, signed by another workflow, repository, branch or for another commit, without provenance, or a digest that moved since the release was first seen: refused, said in `#deploy` with the mention — never built instead; a private or absent package is refused at its anonymous token (GHCR's 403). A registry or sigstore that does not answer (cosign's own words classified: an absent or other signature refuses, the network or TUF waits) is said once, in blue, and waited for an hour, then refused; `docker pull` and cosign are bounded. A « signature » that is only an attestation is refused (cosign v3 takes one for the other, measured). Measured on 29/10, without any token, on public GHCR images: a build provenance verified with these flags, another commit and another workflow refused. `make glorfindel-host-cd-install` brings `published_image.py`, and has the VM fetch cosign (its sha256 kept only if pinned). The transition, step by step: `infra/glorfindel-host/README.md`, « Ce que CI3 change ».
  - **Orodruin gets the published image, verified on the operator's machine** (`make orodruin-push [REF=<tag|commit>]`): resolved, verified and pulled by digest there, loaded over SSH — Orodruin's egress stays closed, GHCR's blobs are served under *.githubusercontent.com, GitHub's domain for user content too, and an NSG filters by address only — under a waiting tag, its image id read back on Orodruin against the ids computed before it left, and only then tagged `eregion-annatar:orodruin`; `~/.eregion-image` is cleared first and written (« commit digest ») on success only. No Terraform change. `make orodruin-push-dev` keeps the former path, the image built on the machine, unverified, said as development (`docs/design/orodruin-contract.md`, « L'image des injecteurs »).
  - What stays open (the threat model): whoever can merge to `main` publishes an image H0 accepts; the SBOM is attested, not read by the CD; Orodruin's image is verified only on the machine that sends it; a deployment of H0 by hand still builds on the VM.
  - Tests `tests/unit/test_published_image.py` (a fake registry, a fake cosign answering as cosign v3.1.3 does, a fake docker), `tests/unit/test_host_cd.py`, `tests/unit/test_workflows.py`; mutants M1650–M1669.

### Changed
- **H0's CD judges the harness's attestation against the lock in service, not in absolute terms** (H3, #324, 29/10; `infra/glorfindel-host/README.md`, « L'attestation du harnais »). The model H0 runs refuses a temperature, and the same lock (litellm 1.100.4) drew 51/51 and no overconfident error, then 50/51 and one: the pair « brute force after root » drew `isolate_vm` twice, then `block_suspicious_ip` at 0.80. Only 15 cases out of 17 drew one action on each pass. The absolute rule (everything right, no overconfident error, one pass) refused at random and asked for the harness again until green.
  - **Two passes, one file.** `make llm-compare MODELS=<H0's model> RUNS=3 ATTEST=1 [BASE=<tag>]` (`scripts/harness_attest.py`) runs the harness on the reference first: the lock of the release in service (the latest `v*` tag, or `BASE`), installed with `--require-hashes` in a throwaway venv under `~/.cache/eregion/`. Then it runs on the candidate (the checkout's `.venv`, refused when it does not follow the lock). The code and the cases are the same; only the dependencies differ. `requirements/harness.json` (`eregion.harness/2`) keeps each pass's `lock_sha256` and `runs`, and per case every draw: right or not, the action, the confidence. Only a rule of ours in its own direction frees its number (`_pair_priorities`).

### Glorfindel — detection and response
- Continuous rule-based detection (RulePoller, one query per rule, rows routed to VMs), assets discovered from their own telemetry (Log Analytics Heartbeat).
- Decision by an LLM (provider-agnostic via LiteLLM) over the enriched signal, a RAG memory of past cycles (ChromaDB) and validated few-shot examples, framed by deterministic guards: executable action, confidence gate, uncharacterized-signal guardrail, attribution, release precondition, autonomy mode, readiness lock. Any model failure escalates; it never acts.
- Autonomy per asset: `human_only` (default) and `non_disruptive`, with a readiness check before a VM leaves `human_only`; observe-only mode on read-only credentials.
- Verified response on Azure: just-in-time isolation by a quarantine NSG (the customer's NSG set aside and restored, compatible with Terraform — measured), Azure DNS and IMDS denied, open sessions cut, every NIC covered, NSG precedence checked, IP blocks in both directions, reassertion every minute, snapshot and restore through Recovery Services Vault with Run Command neutralized before a restore.
- Purple loop: detection rules authored by the LLM, grounded on a technique catalog and the real table schema — reactively on a missed attack, proactively with `propose-rules`; every rule is a proposal a human approves.
- War Room web UI, Discord bot, terminal dashboard; observation kit (`glorfindel verdict`, `glorfindel report`).
