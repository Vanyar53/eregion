# Changelog

Notable changes to Eregion. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/) — before 1.0, signals, schemas and interfaces may still change. Milestones and lots: [`ROADMAP.md`](ROADMAP.md) (French).

## [Unreleased]

### Added
- **The atelier console: Annatar and Gothmog seen from the War Room** (26/10, read only). A second page, `/atelier` (« ⚒ Atelier » in the War Room's header, behind the same token), shows what the injectors ran and what Glorfindel made of it, from the files that reach the War Room's host. Exercises: each window of `runs/exercises/` with its state (open, in grace, closed, or lapsed — never closed, its injector died), the watch's cycles on a target inside it (the return channel's rule, `covering_runs`), the cards carrying its run, and the run's report when it is on the host; a technique expects a detection of its own technique (in a campaign, the next run on the same VM falls in the grace), a fault nothing disruptive, an unattributed detection does not count, and an absence in the host's files is never shown as a miss — only the run's own verdict says `missed`. Campaigns: the manifests of `runs/campaigns/`, and on demand the campaign report's facts (Glorfindel's decision on each run, or why it is unknown) and its `report.md`. Channels: the watch's local heartbeat, the newest window received, and the heartbeat the watch publishes on the return channel — the one a run on Orodruin reads — with the live windows it does not list yet; the detections delivered to a run. Catalogue: techniques and faults, with the last window of each. Every route is a GET (`/api/atelier/{catalog,exercises,campaigns[/<id>],channel,channel/detections/<run_id>}`): a run starts from an armed Orodruin, and a launch button, later, goes through that contract. The War Room never pulls a channel nor writes a window (the watch may purge one, H-1); a campaign's detail says which scenarios its facts leave out, and why. Not on H0 yet: the report of a single Annatar run and of a Gothmog run stay on Orodruin. Tests: `tests/unit/test_atelier_api.py`. Docs: `docs/glorfindel.md`, « Atelier ».
- **A disruptive action runs alone only when several draws of the decision agree** (D-1, #186, 26/10). The same SSH brute force drew `block_suspicious_ip` at 0.80 on 21/10, then `isolate_vm` at 0.78 on 23/10. No temperature was set, so nobody could tell context from draw. Now, when `isolate_vm` or `block_suspicious_ip` is about to run on its own, the model is asked again (`GLORFINDEL_DECISION_DRAWS`, 3 draws in all by default), with the same messages and at the model's default sampling. The action runs only if every draw would have taken it on its own: same action, no escalation, above the confidence threshold. Otherwise the action is held on a new `unstable_decision` card, which can be approved in one click and lists the other draws. A draw whose call fails counts as a disagreement. A malformed value, 1, or more than 10 holds every disruptive autonomous action. A `human_only` VM, or an action another gate already held, pays for no extra draw. Each draw is kept in the cycle's debug line (`decision_draws`). Measured on 26/10 on `claude-sonnet-5-5`: alone, the brute force drew a block in 15 draws out of 15; after root on the same VM, 8 blocks and 7 isolations out of 15. All 5 runs of that case were held, so the 21/10–23/10 swing was the draw. The 4 clear threats ran 12 times out of 12, with no disagreement.
- **The harness publishes what each case drew** (D-1). `scripts/llm_smoke.py` prints each case's actions and confidences over `--runs` (min–max, median), and the gate that held them. It also prints the sampling actually used, how many cases drew a single action, and a pair of cases written in advance: the same brute force alone (expected `block_suspicious_ip`), then after a `sudo` to root on the same VM (expected `isolate_vm`), with a verdict on whether the context moves the decision. `--json` keeps every draw.

### Changed
- **The decision is asked at temperature 0 where the model accepts it** (D-1). `claude-sonnet-5-5`, the default model, refuses it (« `temperature` is deprecated for this model. », measured 26/10), so it is asked again without a temperature, once per process. Each cycle's debug line records the sampling it got: `decision_temperature` is `0.0`, or `null` for the provider's default. `claude-sonnet-4-6` and local models accept 0.

### Fixed

Then it cancels the chaos experiments still running on the bench (they act with their own identity: the revocation does not stop them), deallocates the VM, closes the exercise windows still open in the channel (so the hosted watch stops labelling their targets as exercise after the grace, instead of up to 2 h 15), and says what is left in flight: a Run Command already sent, an atomic cleanup to replay, a VM a cancelled fault may leave down, the grace of a closed window. Any failed step: exit 1. - **The atelier reads enrollment as the watch does** (26/10, #185, after H-1): since H-1 a window marks a VM only if the reader finds it enrolled, a check the watch sets at startup — the War Room did not, so on H0 the atelier would have attached no cycle to any window and kept no run of a published campaign (the tests enroll every VM, which hid it). The War Room now sets the same check at startup (`TagEnrollment`, the host's identity), and the console shows `NOT BELIEVED` (with `window_refusal`'s reason) and `NOT ENROLLED`. ### Security
- **An exercise window is no longer believed on its word** (H-1, #187, 26/10). Anyone who could write a file in `runs/exercises/`, or a blob in the exercise channel, could pass a real attack off as an exercise. The reader now refuses a window that lasts longer than 2 h, starts more than 5 min after it was written (a window written today for tomorrow stays refused tomorrow), or takes the RulePoller's run name (`watch-…`). A window marks a VM only if the watch itself reads the VM as enrolled, from its tags and its resource group's (Azure Resource Manager, cached 10 min). When those tags cannot be read, nothing is marked and every cycle is labelled real. Measured on the bench on 26/10 with the operator's credentials: the bench target is enrolled, the VM carrying a real load is not. A run id marks only a VM its window names. A window is purged a week after its last moment; its tombstone keeps the channel from bringing it back. Exercise cards now stay in the War Room's TO JUDGE list, flagged, instead of being hidden.
- **H0 checks what a campaign brings through the channel** (H-1). Before the report is written, the manifest and each run's report are checked against their shape (`analysis/campaign_schema.py`, `schemas/campaign_manifest.schema.json`, `schemas/run_report.schema.json`). An executed run is kept only if its window is known and believed, names its VM, and that VM is enrolled; otherwise the report says why it was left out. The report also says which facts came through the channel and which H0 saw itself.

## [0.3.0] — 2026-10-23 — "the full loop runs"

The loop runs on the bench, end to end. From an armed Orodruin (O1), Annatar plays a pinned public attack (Atomic Red Team, R1) and Gothmog a declared fault (Chaos Studio, G0) on enrolled targets only (O0), and both verify the initial state after the fact. The hosted Glorfindel (H0) detects and decides in `human_only`, every exercise labelled as such (B2); the run records the detection and its real latency through the return channel (#157, #159). A campaign mixing the atomic with other techniques gets its report written by itself on the hosted Glorfindel, with Glorfindel's decisions and every claim checked against the runs it cites (IA0). Measured on the bench on 23/10: campaign `20261023T081120Z`, 4/4 techniques detected in 101.6 to 130.0 s, its report written once 14 s after publication, 4 decisions attached, 15 claims kept, none rejected. Still running: H0's four-week pre-observation (until about 13/11), then the review point (#70).

### Added

With `EREGION_EXERCISE_CHANNEL`, `annatar campaign run` publishes the finished campaign to the exercise container (`eregion_core/exercise_channel.py`, `publish_campaign`). It publishes `campaigns/<id>/runs/<run_id>.json` for each run, then `campaigns/<id>/manifest.json`, and nothing else. It needs no new right: `REQUIRED_ACTIONS`, the `injector` role and the contract's scope are unchanged. The end-of-run message prints the published id, and announces the report on H0 only for a `done` campaign; otherwise it points to `make campaign-report`. A failed publication is reported, never raised. Windows are untouched: a campaign blob holds a `/`, which `_SAFE_NAME` refuses, and the window pull now pages through the listing. On H0, `glorfindel watch` starts a `campaign-report` thread (`analysis/hosted_report.py`), only with the channel set. Every 30 s it pulls the campaigns into `runs/campaigns/<id>/`: runs first, and a manifest only once all its runs have arrived. A campaign whose pull failed is not due at that pull. The thread writes `report.md` once, under a per-campaign lock, for a `done` campaign whose executed runs all have their report. A failure is noted in `report.error` and counted in memory, so an unwritable `report.error` cannot loop calls to the model. A report is tried at most 3 times; an `aborted` campaign gets no automatic report; no failure reaches the watch. Decisions come from the watch's `watch-*_debug.jsonl` when the run has no `runs/<run_id>_debug.jsonl`, by #157's rule (`first_detection`): same technique, same VM compared without case, seen between the run's finite `attack_time` and the end of its exercise window plus grace (`eregion_core/exercise.py`, `last_moment`, which `live` now uses as its bound). The index is `EREGION_ANALYSIS_INDEX`, else `~/.eregion/analysis/chroma`, mounted from the VM's disk into the watch (`docker-compose.yml`). The Glorfindel image now copies `analysis/`. The mount and the image take effect at the next H0 redeploy. New Make target: `glorfindel-host-campaign-report CAMPAIGN=<id>`. `glorfindel-start`, `-restart` and `-dev` create `~/.eregion/analysis`. Docs: `docs/analysis.md`, `docs/operations.md`, `docs/glorfindel.md`. A report written once now holds the decisions: an executed run, detected or of unknown detection (a silent return channel), whose decision is not yet in the watch's files keeps its campaign waiting, until the end of its window plus grace, or, without a readable window, until 15 min after the campaign's end — then 10 min more (`DECISION_LAG_S`), since the window bounds when the detection was seen, not when the cycle writes its decision: some 25 min after the campaign's end in practice. Without an `attack_time` or a `resource_id` nothing is waited for: the files are whole, nothing could ever be attached. No wait outlasts 2 h 25 after the manifest arrives. The wait and a refused run id are each logged once. Past it, the report is written and says, per run, why the decision is unknown (`fenêtre absente`, `attack_time absent`, `resource_id absent`, `décision non retrouvée dans la fenêtre`; each reads as an unknown, never as a nothing, since the model may copy it into a claim). The model gets `decision: null` with the reason. A found decision shows its action, confidence and escalation, in the table (`snapshot (40%, escaladé)`) and in the facts given to the model (`escalated`). On a run whose decision is unknown, the check rejects a `decision` claim by its kind alone; the rest reads the sentence, so it is a heuristic — a phrasing it does not know passes (`docs/analysis.md`): a trend or an observation that speaks of the response without saying the decision is unknown is rejected (one on the detection alone, « latence en hausse », is kept), and a claim of any kind that says Glorfindel did not act, or that it acted (isolated, blocked, snapshot, escalated, quarantined, contained, intervened, neutralised…), is rejected; the reasons given to the model count as « unknown » where a word begins, so a claim citing « décision non retrouvée dans la fenêtre » is not read as « did not act », while « Glorfindel n'a pris aucune décision dans la fenêtre » is rejected (it passed before the fifth review). Containment words (quarantaine, contenu, contain) also count as speaking of the response. A missed run takes no decision from the `watch-*` files; one found in its window (a late detection, or another run's) makes its decision unknown (`une décision dans la fenêtre d'un run manqué : détection tardive, ou d'un autre run`), never « did not act ». A failed pull of the windows puts the reports off to the next pull instead of writing them. The thread writes only campaigns pulled from the channel (a `.pulled` marker beside the manifest), never a local campaign of the same runs directory. A run id from the manifest that is not a plain name (`safe_part`) is never used as a file name: it is not awaited, it is reported, and its scenario is left out of the facts. On H0, an answer from the model without the tool call is a failed attempt (`build(..., strict=True)`), never an empty report written for good. The in-memory attempt count survives deleting `report.error` (restart the watch to try again). `campaign run --runs-dir X` warns when an executed run has no report to publish (the runs' reports stay in `runs/`), and then does not announce the report on H0. With `--no-report`, the campaign is not published either. A failed pull of the campaigns or the windows, a campaign not all pulled, or a report lock that cannot be opened, is logged once while it lasts (again if it comes back after a pull or an open that went through), not every 30 s; a failure is recognised by its type and HTTP status, not its text (a timed-out connection names an object `at 0x…`, new at every call); a `report.error` that cannot be removed after a report is written no longer escapes `write_report`. The call to the analysis model is bounded (sixth review): `EREGION_ANALYSIS_TIMEOUT_S`, 300 s an attempt (unreadable, zero, negative, infinite or above 3600 → 300; passed to the containers by `docker-compose.yml` and to the Annatar image by the Makefile). It went out with LiteLLM's own default, 6000 s an attempt, so a hung provider held the `campaign-report` thread, and every report after it, for hours without a word; it now times out as a failed attempt, counted, never reaching the watch. It is its own variable, not `GLORFINDEL_LLM_TIMEOUT_S`, which bounds only Glorfindel's calls: the report also runs where Glorfindel's package is not (the Annatar image), and writes up to 2048 tokens off any cycle's path. The Orodruin image must be rebuilt to write `attack_time` into each run's report (without it, no decision is attached), besides H0's redeploy.

## [0.2.0] — 2026-10-15

First release to be tagged; earlier work is in the git history.

### Glorfindel — detection and response
- Continuous rule-based detection (RulePoller, one query per rule, rows routed to VMs), assets discovered from their own telemetry (Log Analytics Heartbeat).
- Decision by an LLM (provider-agnostic via LiteLLM) over the enriched signal, a RAG memory of past cycles (ChromaDB) and validated few-shot examples, framed by deterministic guards: executable action, confidence gate, uncharacterized-signal guardrail, attribution, release precondition, autonomy mode, readiness lock. Any model failure escalates; it never acts.
- Autonomy per asset: `human_only` (default) and `non_disruptive`, with a readiness check before a VM leaves `human_only`; observe-only mode on read-only credentials.
- Verified response on Azure: just-in-time isolation by a quarantine NSG (the customer's NSG set aside and restored, compatible with Terraform — measured), Azure DNS and IMDS denied, open sessions cut, every NIC covered, NSG precedence checked, IP blocks in both directions, reassertion every minute, snapshot and restore through Recovery Services Vault with Run Command neutralized before a restore.
- Purple loop: detection rules authored by the LLM, grounded on a technique catalog and the real table schema — reactively on a missed attack, proactively with `propose-rules`; every rule is a proposal a human approves.
- War Room web UI, Discord bot, terminal dashboard; observation kit (`glorfindel verdict`, `glorfindel report`).

### Annatar — attacks
- Scenarios validated in real runs on Azure: T1486, T1041, T1110.001, T1548.003, T1136.001, and T1110 with T1548 in parallel.
- Generative campaigns: a kill chain composed from the shared technique catalog, optionally LLM-planned, within a scope and a budget.

### Proof
- Hermetic unit tests (no Azure call, no LLM call), property-based invariants on an in-memory Azure whose world moves, a mutation check with a control set, cross-process lock tests, a daily azurerm canary, the Celebrimbor bench (Terraform).
