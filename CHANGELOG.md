### Added
- **Entra ID's logs as a detection source, detection only — the defensive half of C2** (#199, 27/10; stacked on AL1). A source `azure_entra` (`glorfindel/providers/azure/entra.py`, `plane = "identity"`) reads `AuditLogs` and `AADServicePrincipalSignInLogs` from the same workspace (backend `azure_monitor`). Four shipped rules, each with its thresholds and exclusions: a credential added to an application or a service principal (`entra-credential-added`, T1098.001 — secret, certificate, federated credential; a removal is no finding), a consent to an application (`entra-app-consent`, T1528 — delegated or application, admin consent said), a privileged directory role assigned (`entra-privileged-role-assigned`, T1098.003 — permanent, eligible or scoped; PIM activations left out), a service principal's successful sign-in from an address never seen in its 14-day baseline (`entra-sp-unusual-signin`, T1078.004). The adapter applies in code what a query cannot hold alone, tested on fake logs: failures dropped, a role kept only if Entra marks it privileged (`PRIVILEGED_ROLES`, by display name; a role whose name the row lacks is kept), a sign-in kept only for a principal seen on at least 3 days of its baseline. **Nothing is dropped under Glorfindel's identity** (it writes nothing in Entra ID; its usual sign-ins are left out by the baseline, like anyone's): as the actor (`GlorfindelIdentity`) or the target (`GlorfindelManaged`, a credential added to its service principal) a finding is critical, its card first; a customer's identity is never silenced nor marked by it — a name is no proof. **An identity detection is decided by the code, never by the model** (`_identity_decision`, on `context.plane`, the source — `respond` too — or, in depth, the row's Entra columns or table): no `investigate`, no incident, no decision memory — **no UPN reaches the model's provider**, on that cycle or later through `past_cycles` —, no action recommended; escalation `identity_change` whose reason says what, who, on which identity, the grave marks and the severity, and whose **steps say how to check and how to revoke** (remove the credential, revoke the grant, remove the role assignment, block the principal's sign-in — commands for a human). A second lock: the route after `decide` never sends an identity detection to an action, and `escalate_to_human` always types it `identity_change` (never approvable in one click, never folded, no button nor command in Discord). One card per finding (`EventId`), capped per poll with a summary card; an identity rule not projecting `EventId`, or another source reading an Entra table, is said at load. The tables reach the workspace only through a **diagnostic setting on the tenant**: `infra/terraform/entra_logs.tf` proposes it, disabled (`AuditLogs`, `ServicePrincipalSignInLogs` only; disabled, nothing of the tenant is read). Hypotheses to measure on the bench with Jonathan: operation names and the shape of `TargetResources`, latency, licence (sign-in logs in a workspace need Entra ID P1 or P2). After the 5.5 review: under `az login` the token's oid is the operator's, so in Entra ID only an application's token marks Glorfindel (`app_identities`; the Activity Log keeps the oid); a rule of another source reading an Entra table carries `plane: identity` from its query, whatever it projects (the RulePoller and `respond`); the role rule no longer drops an assignment without `Role.DisplayName` (fallback: the role's target; `Company Administrator` added, hypothesis); a first credential's old value is an empty array; a consent card proposes to block only the client application, never the resource's principal; an identity card, or a control-plane one the RulePoller says `unattributed`, is always `real`, never an exercise (a `respond` signal on the Activity Log, with no attribution, keeps its declared window). Out of this lot: the attack side (a public library's technique from Orodruin, R2) and the inscription of an identity. Tests: `tests/unit/test_entra_detection.py`; mutants M920–M949, M955. Docs: `docs/glorfindel.md`, `docs/azure.md`, `docs/design/preuves.md`.
- **Azure's Activity Log as a detection source, detection only** (AL1, #225, 27/10; detached from R2, a prerequisite of C2 and C3). A source `azure_activity` (`glorfindel/providers/azure/activity.py`) reads `AzureActivity` from the same Log Analytics workspace as Perf and Syslog: a rule `source: azure_activity` binds to the `azure_monitor` backend. Three shipped rules, looking back one hour: an NSG or one of its rules written or deleted (`nsg-change-outside-glorfindel`, T1562.007), a role assigned (`role-assignment-write`, T1098.003), a disk snapshot or download access to a disk or a snapshot (`snapshot-by-unexpected-caller`, T1578.001); one row per operation, failures left out. **Glorfindel's own writes** (isolation, quarantine, blocks, release) are dropped by the adapter: its identity — read from its token's claims, `AZURE_CLIENT_ID` and `GLORFINDEL_OWN_CALLERS`, never written in code; from an application's token its `appid`/`azp` and `oid`, from a user's (`az login`) its `oid` only, since there `appid` is the Azure CLI's, the same for the whole tenant (said once) — doing an operation its capabilities declare, **on a target that is its own**: a quarantine NSG, or what an isolation or block state records — the rules it placed (a `glorfindel-*` name on a customer's NSG is no proof: no state names it, the row is kept, critical), a customer rule whose priority it moved, a NIC it put in quarantine; keyed with the state's subscription, remembered two hours after the state is gone. Its identity doing anything else (assigning a role, writing a customer's rule) is kept, marked `GlorfindelIdentity`, `critical`; anyone else writing one of Glorfindel's rules (`glorfindel-*`, its quarantine NSGs) is marked `GlorfindelManaged`, `critical`, its card first. **Each operation has its card** (control-plane rules only): up to five per rule and poll, the gravest first, then one summary card naming every operation left — never a row marked sent without a card; data-plane rules keep one card per cycle. No identity known: nothing is dropped. `normalize_row` gives a control-plane row its operation, target, `caller`, `caller_ip` and both marks; every other row keeps its three keys. The RulePoller deduplicates an operation by its correlation id, operation and target: a row arriving late is a new detection, an operation's Start and Success lines are one; a row on a VM's sub-resource (a role scoped on the VM) is attributed to that VM. A control-plane rule looking back less than 30 minutes, or not projecting `CorrelationId` (two operations at the same instant would fold into one), is said at load. **A control-plane detection is decided by the code, never by the model** (`_control_plane_decision`, on `context.plane` or the source — `respond` too — and, in depth, on the row's `OperationNameValue`: an AzureActivity row read by a rule of another source): no `investigate` on the anchor VM, no call to the model (it would only add text, cost, and send an administrator's name to the provider), **no action recommended**; escalation `control_plane_change` whose reason gives the operation, its status as read (an operation seen at `Start` may fail afterwards: said), the caller, its address, the target, the grave marks and the severity; never approvable in one click, never folded into the previous card, no button nor command on the VM in Discord (nor on `unattributed_signal`). An unattributed control-plane signal opens no incident on its anchor VM, and no control-plane cycle enters the decision memory (ChromaDB). `_SYSTEM_PROMPT`, the few-shot, `_build_user_message` and the data-plane path are unchanged. The `snapshot-by-unexpected-caller` rule rests on a **hypothesis, to measure on the bench**: Azure Backup (Glorfindel's snapshot, a `glorfindel restore`) may produce `disks/beginGetAccess` or `snapshots/write`. `AzureActivity` is **not** in the workspace by default: a diagnostic setting on the subscription sends it there — `infra/terraform/activity_log.tf` proposes it for the bench, disabled (category Administrative only — `Security` is read by no rule; disabled, not even the subscription is read). The replay of a real window of the bench, read only, is left to do with Jonathan. Tests: `tests/unit/test_activity_logs.py` (a fake AzureActivity, no Azure, no LLM); mutants M810–M829, M850–M859, M890–M894. Docs: `docs/glorfindel.md`, `docs/azure.md`, `docs/operations.md`.
- **The analysis AI triages a campaign, with its own memory and model, and nothing applies without a human** (IA1, #88, 27/10, code side). `python -m analysis.triage runs/campaigns/<id>` writes `triage.md` and `triage.json`: what needs a human, computed by the code and sorted by a fixed priority — a missed technique first, then an unknown outcome, an escalation, a scenario in error, a detection slower than the catalog expects. Each item gathers what the code read: the runs (as the report reads them), the technique catalog (checked against its schema when `jsonschema` is there; an invalid one is not believed), Glorfindel's rules (the shipped base and the client's layer over it, read only) and the infrastructure code (is the technique's log source collected? Terraform read without its comments, the evidence cited as `file:line`; a source or a code it cannot read is « unknown », never « not collected »); and the causes of a miss (not in the catalog, no enabled rule, source not collected, collection unknown, or a rule and its source both there). The analysis model explains each item and proposes one of a closed set (`author_rule`, `review_rule`, `check_collection`, `review_decision`, `rerun`); the check removes an entry that names no item, a second one, a proposal the computed facts do not support (`author_rule` while a rule watches the technique…), anything that carries a rule (a KQL query, a rule in YAML), and on an unknown decision an explanation saying Glorfindel acted or did not. Every kept proposal is written `pending` by the code, whatever the model wrote; `python -m analysis.triage decide <campaign> <tri-N> approve|reject --by <name>` records a named human's decision, once, and nothing else — an approved proposal is work for a human, and a triage holding a decision is never written over. The analysis never uses Glorfindel's model nor its memory (`analysis/separation.py`): its model (`EREGION_ANALYSIS_MODEL`) is refused when it is Glorfindel's decision model, compared without case or provider prefix, and its index (`EREGION_ANALYSIS_INDEX`) when it lies in `~/.glorfindel`, path resolved — for the campaign report too; no module of `analysis/` imports Glorfindel or a way to run a command (a test reads the code). Five analysis cases for the harness (`analysis/triage_cases.py`: a miss without a rule, one whose source is collected only in a comment, one with rule and source, an escalation sorted after a miss, a planted line asking for a rule and an approval), run against the real model by `python scripts/analysis_eval.py` (Jonathan) and in the tests with a simulated model. After the review: the triage reads the client's layer as the watch does — an entry the watch skips (no query, `enabled` not a boolean, `interval_s: 30s`, a `ttp` or `name` not a string) no longer replaces the base rule, so a technique the watch still watches is never « no rule » (`tests/unit/test_analysis_rules_parity.py` compares with the watch's own loader on a table of layers); `decide` and the writing of a triage take a `flock` on `runs/campaigns/<id>/.triage.lock` — two decisions at once are both kept (tested across processes); an unreadable `triage.json` (not JSON, an unknown key, kind or status) is refused in one line, exit 1, nothing written and no model called; no turn of the model's prose is filtered (a regex on prose removed legitimate proposals such as « doit être validée par un humain »): what counts is the status the code wrote in `triage.json` — `pending`, or the decision `decide` recorded with the human's name — shown in bold beside each proposal in `triage.md`, whose header says that no decision is taken by the model; the model's text is quoted as its text, on one line (whatever ends a line — `\r` alone, `\r\n`, U+2028… — becomes a space), its Markdown escaped so that it cannot draw a status of its own (tested through a real CommonMark engine, markdown-it, on a table of hostile entries); what the check removed is shown on one line each, its reason written by the code and never quoting the model, escaped too; a new triage written while a decision is taken no longer loses it (the save takes the lock too); Annatar's container receives `GLORFINDEL_LLM_MODEL` (the end of `campaign run` writes its report there, and the refusal compared with the default); `host_env.py` copies `EREGION_ANALYSIS_MODEL` to H0's `host.env`, and `make glorfindel-host-model` says when the model chosen for Glorfindel is the analysis's (`python -m analysis.separation` in the watch exits 2: every report would be refused; 1 is an error, said apart; the target never fails on it); a refusal says what to set first, so the cut message of `campaign run` keeps it. Tests: `tests/unit/test_analysis_separation.py`, `tests/unit/test_analysis_triage.py`, `tests/unit/test_analysis_rules_parity.py`; mutants M780–M799, M840–M842, M844, M871–M878. Docs: `docs/analysis.md`, `docs/design/preuves.md`, `docs/operations.md`, `infra/glorfindel-host/README.md`.

### Fixed
- **A quarantine NSG someone altered is said, even when the isolation's state is lost** (I1F, #226, 27/10, found by the deep run of the invariants — 10 000 sequences): a NIC in Glorfindel's quarantine whose state and NSG tags were lost was never read again — someone turning the quarantine's deny to Udp left the VM reachable on TCP from the VNet (Azure's default `AllowVnetInBound`), and nothing said so. At every interval of the reassertion pass, **whatever the local state** (the pass stopped before any Azure call when nothing was recorded), the watch now reads Glorfindel's quarantine NSGs — the whole subscription's (`list_all`), never only `isolation.quarantine_rg`'s: an NSG made in another group before the setting changed would go unseen — and raises one card per altered NSG holding NICs (`quarantine_altered`, resource = the NSG, high severity), not raised again once acknowledged while the change stands (`~/.glorfindel/quarantine_alerts.json`), closed by itself once the NSG is whole again, empty, or gone from the subscription's listing — never on an NSG read as unknown (unreadable configuration), nor when the listing fails; nothing is written (without a state, nothing says which VM nor its mode). The invariant failure itself (I1 at the very step of the alteration) was the test's: it read a deny of one protocol as a deny-all, so the opening was not counted as someone else's — the test now reads the protocol, grants that exemption only to the quarantine NSGs it altered itself (its journal, as on AWS), and checks the new liveness property L2 (altered → put back or said), with a composite rule that reaches it (`quarantine_altered_then_reasserted`). Regressions in `test_invariant_regressions.py`, mutants M830–M839, M895–M898.
- **The console finds the shipped detection rules wherever it is launched** (#205, 27/10, found by P1's review): since it left `glorfindel/`, the console looked for `detection_rules.yaml` beside its own module — outside the repo's root (an editable install launched elsewhere) the configuration listed no rule, the audit none, and approving a proposed rule answered « detection_rules.yaml not found ». It now finds it as the `glorfindel` command does (H0, run from `/app`, was not affected). Approving a rule says where it went: the client's layer (P1), never the base — added, replaced or already there, and whether it is bound to a VM. A campaign's facts show each run's target VM (D-2). Mutant M409.
- **No test writes in the repository's folder, and the suite fails if one does** (HY1, 27/10, found by IA1's review). `test_store_cycle_never_notifies_a_no_op` called `store_cycle`, which writes `runs/<run_id>_debug.jsonl` relative to the current folder: run alone, it left `runs/run001_debug.jsonl` at the root of the repository or of a worktree. The test now runs in its `tmp_path`, and a session guard in `tests/unit/conftest.py`, armed when the conftest is imported (collection included), fails the run:
  - the writes of the test process under the repository, caches aside, named with the test that made them — this holds where `runs/` already exists, on an operator's checkout. Python's audit hook sees a file opened for writing, a folder made or removed, a file removed, renamed or replaced, a link made, `Path.touch`/`os.utime`/`os.truncate`, `shutil.rmtree` and `sqlite3.connect`. It does not see what a C library writes once a file is open, ChromaDB 1.x's store (written by its Rust core), a path relative to a `dir_fd`, or a subprocess's writes below the root;
  - at the root, whatever wrote it: a new `runs/`, or any new entry git does not ignore.

  Known limits (`docs/operations.md`): another process creating an entry at the root of the main checkout fails the run wrongly; a `TMPDIR` or `--basetemp` inside the repository; `os.makedirs(exist_ok=True)` on an existing folder counts; only `tests/unit/` is guarded. `tests/unit/test_repo_hermetic.py` measures the guard in a throwaway repository. The watch is unchanged. Mutants M910–M914, M950–M952.
- **The quarantine locks' test no longer depends on the order of the files** (HY1). `actions._QUARANTINE_LOCKS` is global: a test of another resource group's quarantine NSG (same name) left its lock, and the check read it. It failed under the harness's load and in reverse order, and `scripts/component_check.py` kept the alphabetical order to avoid it. A fixture now gives the test empty locks. It proves more than before: one key and one lock object for the id and the name, and they exclude each other. A new test checks that two resource groups' quarantines of one name are two locks. Passes alone, in order and reversed. Mutant M915.
- **The injectors' image installs from a lock, with litellm** (HY1). `annatar/Dockerfile` (Annatar's and Gothmog's image, the one `make orodruin-push` sends to Orodruin) installed `.[annatar]` unlocked, and the `annatar` extra did not declare `litellm`: `annatar campaign plan --llm` failed in the image. `litellm==1.86.1` (Glorfindel's pin) joins the extra, with `jsonschema` and `requests`, which the shared core imports (they came only through litellm and azure-core). `requirements/annatar.txt` is generated by `make lock` like `requirements/glorfindel.txt` (constrained by `requirements/dev.txt`); the image installs it with `--require-hashes`, then the project with `--no-deps --no-build-isolation`. `tests/unit/test_dependency_lock.py` covers it. The image on Orodruin must be rebuilt (`make orodruin-push`). Mutants M916–M917.
- **A block the reassertion could not put back is said, even if Glorfindel dies right after** (L1F, #229, 27/10, found by the invariant machine — L1): when re-applying a vanished block failed (the role removed, a lock, a policy), `glorfindel/reassert.py` wrote « already alerted » (`drift_alerted_at`) on the block *before* recording the card. A crash, or a failed card write, in between left the marker without the card, and every later pass returned on that marker: the block gone from Azure, the attacker back in, and nothing said until the block was in place again. The card is recorded first now, then the marker — at worst a card said again at each pass while the marker cannot be written, never silence on a block that could not be put back. The same order for an isolation that could not be put back. Sequence frozen in `tests/unit/test_invariant_regressions.py`, unit tests in `tests/unit/test_reassert.py`; mutants M900–M902. Docs: `docs/glorfindel.md`, `docs/design/preuves.md`.
- **A reset no longer removes another VM's older isolation from an NSG it shares** (I4F, #235, 27/10, found by the invariants at 2 000 sequences, seed 101). An older version's isolation of a VM — its fixed names (`glorfindel-isolation-deny-all`, any/any), its state lost — stays on that VM's own NSG. A new VM is then attached to the same NSG and isolated by quarantine, so its NIC moves away. `glorfindel reset --from-azure` on the new VM read its original NSG to sweep what an earlier fallback left there. It counted only the NICs attached right now: one, the other VM's. It read the NSG as the new VM's alone, took the fixed names for its own, and deleted the other VM's isolation, which reopened that VM. The same held for a NIC left bare. The NIC away now counts among its NSG's NICs, so the NSG reads as shared. The fixed names are no longer the new VM's to take, and the reset says it cannot attribute them (`swept_partial`) instead of deleting them. The release was not affected: it puts the NIC back before reading. Regressions in `test_invariant_regressions.py`, mutants M960–M961.

### Security
- **The Makefile passes every secret by its name** (L23, #228, HY1). `docker run -e AZURE_CLIENT_SECRET=$(…)` (`annatar-run`, `annatar-dry-run`, `annatar-shell`, the `glorfindel-*` targets) showed the value in `ps`, the shell's history and `make -n`. The recipe's shell now chooses the value (`ANNATAR_` / `GLORFINDEL_AZURE_CLIENT_*` first, then `AZURE_CLIENT_*`) and sets it in `docker run`'s environment only; the command line carries `-e AZURE_CLIENT_SECRET`, a name. The canary, `tests/unit/test_makefile_secrets.py`, renders every target with `make -n` and fake values for every secret the Makefile names, then runs the containers' recipes against a fake `docker`. A value the shell expands (`-e NAME="$NAME"`) never reaches `make -n`'s text yet shows in `ps`: the rendered text also refuses `-e NAME=`, `--env NAME=` and, on a line that runs ssh, `export NAME=`, for every secret's name. Mutants M918–M919, M953–M954.
- **The console carries a Content-Security-Policy** (#222, 27/10): `frame-ancestors 'none'` (never framed by another page — Approve & execute under a decoy), `connect-src 'self'` (never talking to another origin, the live feed's WebSocket included), `base-uri 'none'`, `form-action 'self'` — on every response, the token page's included. No `script-src`: the Glorfindel page's inline handlers would break. Mutant M568.

## [0.3.1] — 2026-10-27 — "the defender, hosted and pinned"

### Added
- **Annatar and Gothmog do not act without Glorfindel** (V1, #214, 27/10). Before each run — each run of a campaign too — and before any call to the cloud, `annatar run`, `annatar campaign run`, `gothmog run` and `gothmog preflight` read the watch's heartbeat (`eregion_core/watch_gate.py`): the return channel when `EREGION_WATCH_CHANNEL` is set, else the local `~/.glorfindel/watch_heartbeat`; one younger than 90 s is a live watch. ### Glorfindel — detection and response
- Continuous rule-based detection (RulePoller, one query per rule, rows routed to VMs), assets discovered from their own telemetry (Log Analytics Heartbeat).
- Decision by an LLM (provider-agnostic via LiteLLM) over the enriched signal, a RAG memory of past cycles (ChromaDB) and validated few-shot examples, framed by deterministic guards: executable action, confidence gate, uncharacterized-signal guardrail, attribution, release precondition, autonomy mode, readiness lock. Any model failure escalates; it never acts.
- Autonomy per asset: `human_only` (default) and `non_disruptive`, with a readiness check before a VM leaves `human_only`; observe-only mode on read-only credentials.
- Verified response on Azure: just-in-time isolation by a quarantine NSG (the customer's NSG set aside and restored, compatible with Terraform — measured), Azure DNS and IMDS denied, open sessions cut, every NIC covered, NSG precedence checked, IP blocks in both directions, reassertion every minute, snapshot and restore through Recovery Services Vault with Run Command neutralized before a restore.
- Purple loop: detection rules authored by the LLM, grounded on a technique catalog and the real table schema — reactively on a missed attack, proactively with `propose-rules`; every rule is a proposal a human approves.
- War Room web UI, Discord bot, terminal dashboard; observation kit (`glorfindel verdict`, `glorfindel report`).

### Annatar — attacks
- Scenarios validated in real runs on Azure: T1486, T1041, T1110.001, T1548.003, T1136.001, and T1110 with T1548 in parallel.
- Generative campaigns: a kill chain composed from the shared technique catalog, optionally LLM-planned, within a scope and a budget.

### Proof
- Hermetic unit tests (no Azure call, no LLM call), property-based invariants on an in-memory Azure whose world moves, a mutation check with a control set, cross-process lock tests, a daily azurerm canary, the Celebrimbor bench (Terraform).
