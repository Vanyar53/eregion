### Fixed
- **An operation that succeeded is always read by the shipped Activity Log rules** (AL1d, #600 ; `docs/glorfindel.md`). `nsg-change-outside-glorfindel`, `role-assignment-write` and `snapshot-by-unexpected-caller` keep one row per operation, its latest line, and now count its lines that succeeded in the same `summarize` (`Succeeded`, projected): an operation is set aside only when none of its lines succeeded and its latest is a failure. An operation that only failed still makes no card; the caller exclusions, the other columns and the deduplication by operation are unchanged. The card of an operation whose latest line failed after one succeeded says it took effect. `run-command-by-glorfindel-outside-isolation` keeps every operation, failures included, as before. The sha256 that AL2's tests hold for `snapshot-by-unexpected-caller` follows this change (AL1d changes that rule, not its sister).
- **The same in `restorepoint-by-unexpected-caller`, AL2's sister rule, in its own form** (AL1d, #600 ; `docs/glorfindel.md`, « Les points de restauration »). Its columns still come only from the lines that name a caller other than Azure Backup (`iif(OtherCaller, …)`, the four of them); and only a success that cannot be Azure Backup's counts: `Succeeded = iif(BackupLines > 0, OtherSucceeded, AnySucceeded)` — under a backup's correlation id taken up by someone whose try only failed, Azure Backup's Success (named or bare) makes no card for them; and otherwise the operation is read by its latest line, never by Azure Backup's (`and not(AzureBackup)`): a backup's Success arrived last makes no « (Success) » card for another's failure alone. Said limits: another caller's bare success followed by a failure, under such an id, makes no card; a bare latest Success there may be the backup's and makes one (too many, never one fewer); another caller's Start alone behind Azure Backup's line waits for their success. The limit AL2 wrote down (« an operation read by its latest line, whose failure is left out ») is closed in the rule's description, `docs/glorfindel.md` and the threat model.
- **A latest line that names no caller keeps the caller its operation names** (AL1d, #600 ; `docs/glorfindel.md`). In `nsg-change-outside-glorfindel`, `role-assignment-write`, `snapshot-by-unexpected-caller` and `run-command-by-glorfindel-outside-isolation`, when its latest line names no one, the row of an operation carries `Caller`, `CallerIpAddress`, `CallerAppId` and `CallerObjectId` from the lines that name its caller — **only when they name one** (`Callers = dcountif(strcat(Caller, "|", CallerAppId, "|", CallerObjectId), Named)`, projected; `iif(Fill, …)`): Glorfindel's own writes stay set aside, its identity elsewhere stays critical, and a Run Command is read under the caller its lines name. A correlation id is the client's to choose: filled column by column, two callers' ids were mixed on one row, and one of Glorfindel's sufficed for the adapter to set aside another's rewrite of an isolation rule under the isolation's id, or take another's Run Command for its drain (the 5.5 review). With several callers, the row stays its latest line (bare: naming no one, the critical card of before AL1d on Glorfindel's rule or a Run Command), and the card says its lines name several callers and to read them; a success there is never said to have taken effect. Said limits: one caller named in two forms (a line with Claims, one without) counts as two, its bare latest line left bare as before AL1d; a latest line that *names* Glorfindel under an id someone else took up still decides, as before AL1d.
