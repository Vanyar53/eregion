### Added
- **A sister rule for VM restore points, Azure Backup excluded by its public application id: `restorepoint-by-unexpected-caller`** (AL2, #598 ; `docs/glorfindel.md`, « Les points de restauration » ; `docs/operations.md`, ID1 « Les opérations de test »). Measured on the bench on 05/11 (ID1's hypothesis A2): an on-demand Azure Backup of gondolin — what Glorfindel's `snapshot` action does — goes through restore points (`RESTOREPOINTS/WRITE`, then `RETRIEVESASURIS/ACTION`), never a snapshot nor `BEGINGETACCESS`, so `snapshot-by-unexpected-caller` makes no card at each backup; but `RETRIEVESASURIS` hands out SAS URLs to a restore point's disks, the same exit as a snapshot followed by download access, and no rule read it. Decided by Jonathan on 06/11: a sister rule rather than extending the snapshot rule, which does not change (its sha256 is held by a test). The new rule (`source: azure_activity`, detection only, `plane: control`, T1578.001 and T1530, `high`, `critical` under Glorfindel's identity) reads `RESTOREPOINTS/WRITE`, `RESTOREPOINTS/RETRIEVESASURIS/ACTION` and `RESTOREPOINTS/DISKRESTOREPOINTS/BEGINGETACCESS/ACTION` (the same URL through the public API, disk by disk) — not a collection written alone, which holds nothing; one row per operation, its latest line, failures left out. **Azure Backup is excluded, and it alone, by its public application id** (`262044b1-e2ce-469f-a196-69ab7ada62d3`, the same in every tenant of the public cloud: Microsoft Learn, « Back up and restore Azure VMs with PowerShell »), in `Claims.appid` or as the `Caller`: an operation makes a card when one of its lines names a caller other than Azure Backup; a line that names no one decides nothing — a backup's last line may carry neither, and its Start line may be out of the window or not yet ingested: anyone else's card comes at the pass where their named line lands. A correlation id is the client's to choose (`x-ms-correlation-request-id`), so a backup's id taken up by someone else hides no one; Azure Backup's id is matched whole, never as a term of the `Caller`. The row carries the caller that decided it: its latest line's when that line names someone other than Azure Backup, else another caller one of its lines names (a bare latest line, or Azure Backup's) — so Glorfindel's Start followed by a bare Success is critical, and a human's names the human; when several other callers share an operation, the card names one and its severity follows that one. Its card is decided by the code, no action, like every control-plane card. It does not see a restore or a file recovery from the vault, a storage SAS (`LISTSERVICESAS`), the download itself, what Azure Backup does under its own identity, an operation none of whose lines names a caller, nor — a known limit of the family of activity-log rules, followed by AL1d (#600) — an operation read by its latest line, whose failure is left out. The bench proof is written for Jonathan: a backup makes no card; a restore point of gondolin made by hand, then download access to its disk, make two; the `az` commands are reversible, and a query confirms Azure Backup's caller on the 05/11 lines (hypotheses ID1-A9, ID1-A10; the query also shows whether an operation's last line is bare). The test reader `kql_subset` now follows `parse_json(…).member`, `["key"]`, `in~`, `!in~`, `arg_max(…, *)` followed by named aggregations, `take_anyif` and `iif`. `!~`, which no rule uses, is left out of it.
  - Tests: `tests/unit/test_restore_points.py` (the rule as written over forged AzureActivity lines, then the real AzureActivityDetector and the RulePoller; no Azure, no model). Mutants M4280–M4289, M4305–M4309 and M4390–M4392.
