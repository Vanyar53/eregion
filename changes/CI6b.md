### Fixed
- **The mutation harness makes ChromaDB's embedding model ready once, before any run in parallel** (CI6b, #538; `docs/operations.md`, « La porte de release »). At the release gate's first real run (the 0.5.5's pull request, #537, 05/11), two shards of fourteen failed on the unmutated code (`FileNotFoundError … onnx.tar.gz`, `InvalidProtobuf`): since CI6, the unmutated runs start at once (`--jobs 4`), and on a fresh runner each pytest fetched the model (about 80 MB) into the same `~/.cache/chroma`, reading another's half-written file.
  - **`scripts/mutation_check.py`** calls ChromaDB's default embedding function once on a word, in its own process, before the unmutated runs and the mutants' (`prepare_embedding_model`): chromadb 1.5.9 fetches the model only when one of its files is missing, checks the archive's SHA-256, and loads it as a test would. The model there, nothing goes out; ChromaDB absent, nothing to prepare. The runs inherit the harness's `HOME`, so they read the same `~/.cache/chroma`. The Monday measure (`mutants.yml`) and a local run gain the same.
  - **A preparation that fails is said** (without a network, a corrupt cache), its error whole, with what to do; the runs then go on as before, each free to fetch the model itself. It is never a verdict: it neither stops a shard nor catches a mutant.
  - **`.github/workflows/release-gate.yml`**: the `mutants` and `control` jobs restore the `chroma-onnx-v1` cache, as the `invariants` job and `ci.yml` do, by the same action pinned by commit.
  - Tests: `tests/unit/test_mutation_shards.py` (prepared once, before any run, never by each; by the default embedding function, on a fake ChromaDB; nothing without ChromaDB; a failure said and the runs on, no mutant caught by it; the runs' `HOME` the harness's; with the model there, chromadb itself never downloads), `tests/unit/test_workflows.py` (the invariants, mutants and control jobs restore the model before their tests, one pinned action, ci.yml's key). Mutants M3730–M3734 (`scripts/mutants/CI6b.py`).
