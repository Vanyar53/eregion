### Added
- **Orodruin up to date at its start: after a publication, `make orodruin-start` is enough** (OI3, #522; `infra/orodruin/README.md`, « À jour au démarrage »; `docs/design/orodruin-contract.md`, « L'image des injecteurs »; `docs/operations.md`). H0 deployed the 0.5.4 by itself (its CD); Orodruin, stopped most of the time and without egress to the registry, stayed on the 0.5.3 until a `make orodruin-push REF=v0.5.4` by hand.
  - **`make orodruin-start`**: the VM started, then awaited over SSH (`ssh-keyscan`, nothing accepted there; 2 minutes at most), `orodruin-update` checks Orodruin's host key (`orodruin-known`) and reads the image in service in read-only, through the pinned key — docker answering (`docker info`), the tag `eregion-annatar:orodruin` and the commit its label `org.opencontainers.image.revision` says, then `~/.eregion-image` (at most 4 KB; the read bounded on the workstation too). `scripts/published_image.py age` compares it, on the workstation, to the latest release: the highest tag `v*` by version order (`v0.5.10` after `v0.5.9`, as `orodruin-push` takes it without `REF`), then by commit in git's history (`merge-base --is-ancestor`), never two strings.
  - **Older, absent or unreadable** (a verified marker whose tag says another commit included: an `orodruin-push-dev` cut before its marker): said, then `make orodruin-push REF=<the release>` as it is — digest, signature, provenance, the archive of the blobs, the load, the read-back, OI2's control run, the tag, the migration. **Equal**: nothing, in one line. **Newer** (a commit of `main` pushed by hand), **dev** (`orodruin-push-dev`) or off the release's history: kept, never replaced unless asked, the command to go back to the release said.
  - **On any error** (the VM not answering, docker not answering on Orodruin — never taken for an image absent, whose push would erase `~/.eregion-image` first —, the read, an image's commit unknown here, a `REF` off `origin/main`, the push, its verification, its control run): a non-zero exit, the cause said, nothing armed, and the VM left started — said too. `NO_UPDATE=1` starts without reading or changing anything, and says so; `REF=<tag|commit>` aims at another release. Both are given on the command line, checked before anything (`az` included), read by the shell from its environment, never expanded by make; from the environment, refused. Before `az vm start` too: `ORO_SSH_FINGERPRINT` set (but under `NO_UPDATE=1`) and `ORO_CHECK_TIMEOUT`. `make -n orodruin-start` runs nothing: the next make is never written `$(MAKE)` in the recipe. `make orodruin-update [REF=…]`: the same update, the VM already started.
  - **`make orodruin-check`** says, before the verdict, « image vX (commit), dernière release vY (commit) », and when older, absent or unreadable « image plus ancienne (absente, illisible) : make orodruin-start ou make orodruin-push REF=vY »: a warning, its exit code stays the contract's. Nothing changes to Orodruin's network, its contract, its watch guard, `orodruin-push` or `orodruin-push-dev`.
  - Tests: `test_published_image.py` (the targets run on OI1's and OI2's fakes, with a throwaway git repository — `v0.5.9`, `v0.5.10`, a commit after, a branch beside — and the host key really checked by `known_host.sh`: older pushed, absent and unreadable pushed, a marker its tag contradicts pushed, equal left in one line, newer, dev and diverged kept, a failed push non-zero with `:orodruin` unchanged, docker down, an unknown commit and a `REF` off main decide nothing, a VM that never answers, `NO_UPDATE=1`, `REF=`, thirteen values refused before `az`, the dry run; `orodruin-check`'s warnings), `test_host_ssh.py` (the update's and the check's SSH, each with the pinned key, ed25519 only, never accept-new). Mutants M3630–M3639 and M3685–M3693 (`scripts/mutants/OI3.py`): all caught.

### Fixed
- **Orodruin's first deployment: no `YES=1` on a plan that was not the one read** (OI3's review; `infra/orodruin/README.md`, « Déroulé »; `docs/banc-bl1.md`). `make orodruin-plan` computes the plan with the egress closed (`egress_locked=true`), while `make orodruin-up` applies it open: `orodruin-up YES=1` after `orodruin-plan` applied a plan no one had read. Each apply now shows its plan and waits for its confirmation; the first opens the egress, the second (`orodruin-lock`) closes it.
