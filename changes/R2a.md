### Added
- **The Stratus Red Team adapter (R2a, part of #79)**: Annatar can run an Azure control-plane technique by **calling the public Stratus Red Team binary** (DataDog, Apache-2.0, v2.38.0) by its technique id — no home-grown offensive logic. `annatar/engines/stratus.py` resolves an id against a **closed allow-list** (the `engine: stratus` entries of `technique_catalog.yaml`) and, for an allowed technique, hands the runner the exact argv of each phase of Stratus's own cycle; `annatar/executors/stratus_host.py` runs them from an **armed Orodruin**. The `warmup → detonate → revert → cleanup` cycle is **mapped onto the injector interface** (prepare, inject, revert, clean up). Modelled on the Atomic adapter (R1, `annatar/engines/atomic.py`). The binary is **pinned** (`annatar/stratus/PIN`) and its sha256 **re-checked before every phase** (SEC5) — a binary that is not the pinned one, or one swapped mid-run, runs nothing. `stratus` joins `KNOWN_ENGINES` (`annatar/runner/parser.py`) and the runner dispatches it (`Engine._run_stratus`). Three Azure techniques in the catalog (`azure_control_plane`, `status: planned`): `azure.execution.vm-run-command` (T1651), `azure.persistence.create-bastion-shareable-link` (T1133), `azure.persistence.backdoor-managed-identity-fic` (T1098). They show in the Azure Activity Log (`azure_activity`, detection lot AL1); the real bench measurement is **ID1 (#281)**, so `attack_started` is emitted but the detection is not waited on (`detection: unknown`, said in the report).
  - Tests: `tests/unit/test_annatar_stratus.py` (hermetic, fake Stratus, `dry_run`, no cloud/LLM call). Mutants M4315–M4354 (`scripts/mutants/R2a.py`).

### Security
- **Fail closed on the id and the allow-list**: a technique id not shaped `azure.<tactic>.<name>` (non-Azure platform, path separator, option-looking segment, space, upper case) is refused before it reaches a process; an id Stratus knows but the catalog does not is refused too. The binary's sha256 is re-verified before every phase.
- **Bench only, enrolled, on the control plane**: `Engine._run_stratus` guards the bench group — inside the bench, enrolled (`eregion-target`/`eregion-zone`, the group standing for the target), and in zone **`bench` only** (a Stratus technique can create real cloud resources, so it never runs in twin or production). Whether Stratus provisions inside that group or creates its own (then outside the inscription and the exercise window) is a design question for R2b/ID1, not settled here.
- **Every phase goes through the Orodruin contract and is journaled** before it runs, and counted against the cap (`Session.before_call`), like the VM executor. With no armed contract: passive, nothing touched (`Passive`). The **Graph probe is read-only**: held to a GET of a Microsoft Graph v1.0 path (it can only read the directory), it checks the initial state before `detonate` and after `cleanup`, journaled as a declared read (never counted against the cap). `warmup` creates the prerequisites, so **cleanup always runs** (even when warmup or detonate raised); revert runs only after a detonation.
- **Orodruin has no Internet**: `warmup` provisions with Terraform (pinned `1.3.10`, which the catalog auto-installs otherwise) and its provider plugins; both are embedded and pinned in the image, and the adapter points Terraform at them offline (`airgap_env`: a run-scoped `HOME`, `TF_PLUGIN_CACHE_DIR`, a `TF_CLI_CONFIG_FILE` filesystem mirror) — `terraform init` never reaches the network (`annatar/stratus/README.md`, `annatar/stratus/PIN`).
