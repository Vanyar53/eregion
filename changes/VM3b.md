### Security
- **The catalog decides an atomic scenario's steady-state probes too** (VM3b, #568; `docs/azure.md`, « Les sondes aussi »). A probe's `verify` is a command Run Command runs as root, three times a run: `catalog_destructive` now compares the scenario's `steady_state` probes to its entry's — in order, `verify` and `expect` included — as it already compared `engine_ref`, `engine_args` and `revert`. Another probe makes the run unknown, so destructive: refused in production, and refused everywhere when the scenario calls itself `destructive: false`. The four shipped atomic scenarios, R1's `account-creation-atomic` included, have exactly their entry's probes.
  - Tests: `tests/unit/test_vm3b_suites.py`; mutants M4100–M4102 (`scripts/mutants/VM3b.py`).
- **An `engine_args` value never starts with `-`** (VM3b, #568; `annatar/engines/atomic.py`). In an argument's place, `-rf` or `--help` would be an option of the command it lands in, not a value: the adapter refuses it before anything is armed, as it refuses a value outside `[A-Za-z0-9._/:-]`.
  - Tests: `tests/unit/test_vm3b_suites.py`; mutant M4108.

### Fixed
- **T1053.003's revert waits on a probe, not on the call** (VM3b, #568; `annatar/runner/engine.py`, `annatar/engines/atomic.py`, both schemas; `docs/azure.md`). Each step of an atomic's `revert` now names the steady-state probe it waits on (`requires_probe`, one of the scenario's probes, else refused before the contract is armed): after the cleanup, that probe runs, and the step runs only once it holds again. Run Command does not raise on a script that failed, so a cleanup whose call passed no longer lets `/tmp/notevil` — root's crontab — be removed while the evil line is still installed: the revert is skipped, the file stays for the operator, and the run says so (`checks.revert: SKIPPED`, `metrics.revert_skipped`, the run's error). A gate probe that raises is no proof. The call cap counts the gate probe. T1053.003's revert waits on `cron-entry-absent` (ABSENT), in the catalog and the scenario.
  - Tests: `tests/unit/test_vm3b_suites.py`, `tests/unit/test_vm3_pairs.py`; mutants M4103–M4107.
- **`t1070-002-log-tamper` sets the Azure agent aside more narrowly, and says what it cannot** (VM3b, #568; `glorfindel/rules/azure/detection_rules.yaml`; `docs/azure.md`, « L'agent Azure dans `log_tamper` »). python3 is set aside only as the system's interpreter (`/usr/bin/python3` or `python3.N` exactly, no longer any exe that begins so), on `/var/log/azure/`, `waagent.log` and `unattended-upgrades`; the agent's binaries (`/var/lib/waagent/`, `/opt/microsoft/`) on `/var/log/azure/` only. Dropping python3 would lose the real noise — waagent, the monitoring agent's handler and unattended-upgrades are scripts, their `exe` is the interpreter, and auditd does not name the script — so the limit is written in the rule and the doc: any python3 script writing those files is not seen. The same holds for logrotate, set aside on all of `/var/log` since rotating every log is its job.
  - Tests: `tests/unit/test_vm3b_suites.py`; mutant M4109.
