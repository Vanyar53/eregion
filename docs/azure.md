# Azure — détails à connaître

_Extrait tel quel de `CLAUDE.md` le 2026-10-15 (lot DX1) : le comportement d'Azure tel que mesuré sur le banc, et les pièges opérateur. Les règles de sûreté et les conventions restent dans `CLAUDE.md`._

## Détails Azure à connaître

- NSG isolation = outbound deny-all → bloque AMA (`mdsd.err` : Failed to get gig token) → detection timeout sur run suivant. Toujours `glorfindel reset` avant le prochain run.
- `annatar clean` T1486 génère des I/O disque élevées → RulePoller peut matcher la règle `ransomware-disk-write` (données dans `ago(10m)`) avant le vrai run. Résultat : `detection_time_s=0`, isolation sur données du nettoyage, pas du vrai run. Fix : attendre 10 min entre `annatar clean` et `annatar run`, ou vérifier que `detection_time_s > 0` après le run.
- **Multi-NIC — isolation/block couvrent TOUTES les NICs** : un NSG s'associe à un **subnet** OU une **NIC** (≤1 chacun ; un même NSG peut être partagé entre plusieurs subnets/NICs). Une NIC est soumise à ≤2 NSG (le sien + celui de son subnet). Une VM a 1..N NICs, chacune avec 1..N ipConfigs (IP privées multiples). **Ne couvrir que la NIC primaire laisse les autres NICs ouvertes** (faux « isolé »). `_get_vm_nic_targets(rg, vm)` énumère toutes les NICs → `isolate_vm`/`block_suspicious_ip(scope="vm")` posent **un placement par NIC** : deny any/any sur un NSG de NIC (première priorité libre ≥ 100 — **aucune règle client déplacée** depuis le lot L3), ou deny **scopé à TOUTES les IP privées de la NIC** (règle augmentée `*_address_prefixes`) sur un NSG subnet partagé (priorité libre, pas de bump). Noms de règle uniques par (VM, NIC) via `_placement_rule_base` (hash si > 80 char). `release_isolation`/`unblock_ip` défont chaque placement ; `verify_isolation`/`verify_block_ip` renvoient `verified=False` si **une seule** NIC n'est pas couverte (`uncovered_nics`). State : liste `placements[]` dans `isolation/<vm>.json` et entrée block (+ champs plats `nsg`/`nsg_scope` rétro-compat `/api/state`). **Rétro-compat** : release/verify gèrent l'ancien state single-NSG. ⚠️ `verify` confirme la **présence des règles par NIC** (pas l'API *effective security rules* — écartée : nom SDK non vérifiable hors Azure + flaky VM éteinte). ⚠️ **Phase B (backlog)** : les couches AU-DESSUS du NSG peuvent court-circuiter l'isolation et ne sont PAS encore détectées — **Azure Virtual Network Manager security admin rules** (`Always allow` globale, priorité > NSG), **UDR/route tables/Azure Firewall** (routage), **ASG**, IPs plateforme `168.63.129.16`/`169.254.169.254`. Voir mémoire `reference_azure_nsg_model`. **✅ Phase A validée sur Azure réel 2026-06-25** (topo Celebrimbor `multinic`, 2 NICs/2 NSG scope-NIC, PASS 7/7) : isolate pose la deny sur **les 2** NSG, `verify_isolation` `verified=True nics_covered=2`, retrait manuel d'une règle → `uncovered_nics` détecté, release/block/unblock multi-NIC propres. Le trou « 2e NIC joignable malgré ISOLATED » est **fermé et vérifié** (plus seulement mocké).
- **Précédence des règles NSG — une allow avant notre deny l'emporte (constat banc 2026-10-05)** : les NSG appliquent la **première** règle qui correspond, par priorité croissante. Le NSG de subnet du banc portait `allow-ssh` (Inbound, * → *, 22) en **priorité 100** : l'isolation (deny IP-scopé à la 1re priorité libre → 101) laissait **SSH ouvert** sur la VM « isolée », et `block_suspicious_ip` (deny à partir de 200) laissait passer un **brute force SSH** — pendant que la vérification, de présence seule, disait `verified=True`. Désormais : `_shadowing_rules()` (allow hors `glorfindel-*`, priorité < notre deny, source ET destination couvrant le trafic visé ; CIDR, `*`, `VirtualNetwork`/`Internet`, ASG supposé couvrant) → `shadowed_by` dans l'outcome (blocage de périmètre compris), **`verify_isolation` / `verify_block_ip` échouent** (escalade `verification_failed` qui nomme la règle — type réellement émis depuis la seconde passe du 05/10 : `escalate_to_human` n'avait pas de branche pour un échec de vérification, qui arrivait étiqueté « detection timeout », sans bouton Revert), et l'**audit** a un contrôle « NSG precedence » (fail + commande `az network nsg rule update … --priority 1000`). **Lot L3 (2026-10-06)** : plus aucune règle client n'est déplacée (avant : une règle client en priorité 100 passait à 200 pour laisser la place au deny — un `terraform apply` la remettait, ou échouait sur notre priorité) ; le deny prend la première priorité libre, sur **tout** NSG, et la préséance est donc vérifiée partout. Quand une allow passe avant notre deny sur le NSG de la carte, le deny est posé sur le **NSG du subnet** (`alt_nsg`, scopé aux IP de la VM ; le trafic doit passer les deux NSG, un deny dans l'un suffit), placement noté `moved_from` ; vérification, levée sans état et `reset --from-azure` regardent les deux NSG (`_nic_nsg_views`). **Liste des règles illisible** (throttling, erreur transitoire) → `verified=None` + `precedence_unknown` (« préséance non vérifiable »), plus `verified=True` sur une inconnue ; l'audit passe en `warn` ; `reset --from-azure` garde l'état local. Le contrôle d'ombrage utilise le nom de règle **trouvé** (une isolation au nom legacy passait sans comparaison). **Blocage gradué par port (L3)** : le port de la menace est déduit de la détection, jamais ajouté au signal (règle `ssh-*`, ligne qui mentionne ssh, requête de la règle du TTP avec `sshd`/`Failed password` → 22) et passé à `block_suspicious_ip(threat_port=)`, enregistré dans l'état. Une allow **entrante** avant le deny ne contourne le blocage que si elle **couvre ce port** (`threat_port_open`) ; sinon c'est une **exposition** (`exposure` : l'attaquant atteint d'autres ports), vérification OK. Une allow **sortante** avant le deny est toujours un contournement (A0, décidé avec Jonathan le 12/10 : la VM joint encore l'attaquant — reverse shell, exfiltration). Port inconnu → toute allow compte, comme avant. Le NSG de repli s'applique aussi aux blocages. Banc : `allow-ssh` passé à **1000** (`network.tf`, appliqué le 05/10 ; topo multinic aussi) — **Glorfindel utilise la plage 100–999, les allow client doivent être au-delà**. Validé en réel le 05/10 : isolate (deny à 100) → `verify_isolation` OK → release → `verify_release` OK ; block (IP de doc 203.0.113.50) → `verify_block_ip` OK (deux sens) → unblock ; aucune règle ni état résiduel.
- ⚠️ **NSG Terraform à règles EN LIGNE** (`network.tf`, topos) : un `terraform apply` / `make celebrimbor-up` **supprime toute règle absente du fichier — y compris les `glorfindel-*` d'une isolation ou d'un blocage en cours**. `glorfindel list` doit être vide avant un apply.
- **NSG de NIC partagé — traité comme un NSG partagé (revue 2026-10)** : un même NSG peut être attaché à plusieurs NICs (pattern « un NSG par tier ») ou aussi à un subnet. L'ancien code le traitait comme « cette VM seule » et y posait un deny any/any priorité 100 → une isolation **autonome** coupait **toutes** les VMs derrière ce NSG (et deux placements sur le même NSG entraient en conflit de priorité). `_nsg_is_shared()` lit `network_interfaces`/`subnets` du NSG ; partagé (ou illisible) → `ip_scoped=True` → deny scopé aux IP de la VM, priorité libre, aucun bump (même traitement qu'un NSG subnet). Le scope affiché reste `nic` + `shared_nsg: true`. ⚠️ À valider sur Azure réel : topo `sharednsg` (`topo_sharednsg.tf`, désactivée par défaut — `make celebrimbor-up TOPO=sharednsg`, puis `make celebrimbor-down TOPO=sharednsg`). Le banc baseline n'a pas ce cas (NSG de subnet uniquement).
- **Échec partiel isolate/block** : un échec sur la NIC n laissait les règles des NICs 1..n-1 sur Azure **sans état** (invisible de `list`, hors d'atteinte de `reset`). Désormais les règles posées **restent** (confinement partiel > aucun), sont enregistrées (`partial: true`, `failed_nic`) et `PartialActionError` est levée (porte le `status_code` → `write_blocked` préservé). Les règles client décalées de la priorité 100 sont enregistrées **dès** que le décalage est confirmé ; si le deny échoue ensuite, elles sont remises à 100 immédiatement.
- **`release_isolation` / `unblock_ip` ne mentent plus** : les erreurs de suppression ne sont plus avalées (`ResourceNotFound` = déjà supprimée, OK) → statut `release_partial` / `unblock_partial` + règles en échec, **état conservé** pour un nouvel essai (la réaffirmation le laisse à l'opérateur ; l'IP bloquée de nouveau **en entier**, le blocage remplace le déblocage, ses marques s'effacent et il est de nouveau vérifié — L1B, #355 : `_save_block_state` fusionnait sans les retirer, et ses règles disparues n'étaient plus jamais dites) ; `glorfindel release`/`unblock`/`reset` le disent et sortent en code 2 (la War Room affiche donc une erreur). Sans état (perdu, corrompu, jamais écrit) : `release` recalcule les noms de règles (déterministes) sur **chaque** NIC actuelle — couvre en partie le follow-up « reset source de vérité = Azure ». État illisible → avertissement, les règles retrouvées par leur nom (plus de crash) — une carte en quarantaine ou sans NSG attend qu'il soit réparé (SEC4b, ci-dessous). Écritures d'état atomiques (tmp + `os.replace`). `glorfindel release` ne dit « rien à lever » que si **aucune** NIC ne porte de règle (avant : `not verify_isolation()` → une VM à moitié isolée voyait son état effacé, règle orpheline). **VM supprimée** (I7S, #303) : ses cartes sont parties avec elle, leurs NSG ne se demandent plus ; la levée cherche donc les règles nommées pour les cartes que ses états nomment (placements de l'isolation et des blocages, l'empreinte de la carte dans le nom) sur **tous** les NSG de l'abonnement, et les retire — une isolation dont l'état avait été perdu ou réécrit depuis restait sur un NSG partagé, visant l'adresse que reçoit la VM suivante. Une liste des NSG qui échoue donne `release_partial` (« levée non vérifiée »), l'état gardé avec ses cartes (`known_nics`) pour le nouvel essai. Un état de la VM illisible (isolation ou blocage) peut nommer des cartes que rien d'autre ne nomme : `release_partial` (« supprimée, état illisible »), le fichier gardé tel quel — la levée effaçait le seul fichier qui nommait la carte. Chaque carte connue est **lue d'abord** : `az vm delete` et Terraform gardent la carte par défaut, détachée. Introuvable (404), détachée ou rattachée à une VM d'un autre nom : ses règles sont cherchées. Rattachée à une autre VM du **même nom** (un autre groupe), l'isolation de celle-ci porte les mêmes noms : laissées, et dit (`release_partial`) — la levée de l'autre VM les retire ; si elle n'est pas isolée (`glorfindel status`), ce sont celles de la VM supprimée, à retirer à la main (`az network nsg rule delete`). Illisible : « levée non vérifiée ». Limites : sans aucun état qui nomme la carte, rien ne dit quoi chercher (le balayage des orphelines, A3, reste le filet) ; un NSG que l'identité ne lit plus manque à la liste sans erreur (hypothèse I1S) ; seuls les noms actuels à empreinte sont cherchés, ni ceux d'avant L24 ni ceux suffixés par la VM, partagés par des homonymes (voulu, I2). **Un refus qui retient une règle retournée** (I5Q, #327) : quand une carte vivante a repris l'adresse qu'un refus de la VM supprimée vise, sur un NSG qui la gouverne, et qu'une de nos règles retournée en autorisation par quelqu'un (du même côté, visant cette adresse ou toutes) se tient sur un NSG de cette carte, la levée garde ce refus — le retirer laisserait passer ce que l'autorisation ouvre, devant notre blocage — et dit `release_partial`, la règle retournée nommée ; une fois celle-ci remise en refus ou retirée, la levée suivante le retire. Le balayage des orphelines fait de même (`docs/glorfindel.md`).
- **État local illisible — un inconnu, jamais « rien » (SEC4b, #275, 29/10)** : un fichier d'isolation qui ne se lit pas (JSON cassé, ou pas la forme qu'écrit Glorfindel : un objet dont les `placements` sont une liste d'objets ; `unreadable_states`) peut tenir n'importe quelle carte. SEC3 l'avait fermé pour le balayage des orphelines ; les autres lecteurs qui concluaient « personne » d'une absence s'arrêtent aussi. `_recorded_original` et `_held_in_quarantine` lèvent `StateUnreadable` quand aucun état lisible ne nomme la carte et qu'un état est illisible — l'original qu'il tient l'emporte sur notre tag, qu'on ne lit donc pas à sa place. D'où : la levée et `reset --from-azure` ne retirent rien d'une carte en quarantaine ou laissée sans NSG et ne disent pas levé (`release_partial`, `swept_partial`, le fichier nommé) ; `verify_release` ne dit pas vérifié (`unreadable`) ; les noms fixes d'une ancienne version sur un NSG restent et sont dits (`_tied_while_away` → inconnu) ; une levée en échec n'écrit plus par-dessus le fichier illisible de sa VM (écrit par-dessus, ce qu'il tenait était perdu et la levée suivante lisait notre tag à sa place). Un déblocage derrière la quarantaine (le NSG propre de la carte, que seul l'état ou notre tag nomme) finit en `unblock_partial`, le fichier nommé. **L'isolation, elle, n'est jamais arrêtée par un état illisible** (relecture de SEC4b) : `_recorded_or_unknown` / `_held_or_unreadable` lisent l'illisible comme inconnu — notre tag s'il dit l'original, sinon l'original n'est pas écrit et la levée gardera la carte en quarantaine jusqu'à ce qu'il soit connu (le tag, `glorfindel-orig-<hash>=<id du NSG>` ou `none`, que l'erreur de la levée nomme). L'état illisible de la VM isolée n'est jamais écrit par-dessus : le nouvel état le met de côté, dans `isolation/aside/` — hors des `*.json` des états : jamais plus un état, réparé ou non (ni `active_isolations`, ni la migration, ni la recherche de l'état d'une VM ne le lisent), listé par `unreadable_states` tant qu'il existe ; la carte demande de le lire, de reporter à la main dans l'état courant ce qui y manque, puis de le retirer (seconde relecture : mis de côté en `<fichier>.unreadable.json`, réparé, il redevenait une seconde isolation de la VM, et la migration le remettait à la place de l'état courant). Une isolation qui laisse l'original d'une carte inconnu le dit tout de suite : `original_unknown` dans son résultat (`original_note`) et dans son état, « ⚠ original unknown » sur la carte de la VM dans la console — une levée autonome (`recovery_complete`) s'arrêtera sur le tag ; la carte `state_unreadable` le rappelle. La réaffirmation le dit (carte `state_unreadable`, ci-dessous ; seul le balayage des orphelines attend quand seuls des fichiers de blocage sont illisibles). Un état à `placements` sans `resource_id` est illisible ; seul un état d'avant les placements (#8, 06/19) peut ne pas en porter. **Coût assumé** : tant qu'un fichier est illisible, ces opérations attendent, pour toute VM dont une carte est en quarantaine ou sans NSG — un état d'une autre VM peut nommer cette carte (une carte déplacée d'une VM à l'autre). Sortie : réparer le fichier ou le retirer à la main, puis relancer. Une isolation par règles seules (aucune carte en quarantaine ni nue) se lève comme avant : les noms sont déterministes. Tests : `tests/unit/test_unreadable_state.py`.
- **La réaffirmation et les contournements (V-16, SEC4b)** : la réaffirmation reposait les règles **disparues** et se taisait quand une isolation ou un blocage était **contourné** — une règle d'autorisation d'un tiers évaluée avant nos refus, sur le NSG de la carte ou du sous-réseau (`shadowed_by` de `verify_isolation` / `verify_block_ip`, `_shadowing_rules`). Remettre nos règles n'y change rien, et Glorfindel ne retire jamais la règle d'un tiers (I2) : il le dit, sur une carte `bypassed` (action `review_bypass`, rien d'exécutable, sévérité haute) qui nomme la règle, sa priorité, son sens, ses ports et son NSG — **une par isolation ou par blocage (IP) et par changement** : pas à chaque passe, pas de nouveau une fois acquittée (`bypass_said` dans l'état, écrit après la carte, L1F). Elle se ferme quand le deny tient de nouveau ; une préséance illisible, ou des règles disparues (la carte de dérive le dit), la gardent. Pour un blocage, seul ce qui laisse passer la menace compte (`threat_port_open`) — une exposition d'autres ports reste une vérification OK. **Contournée et disparue à la fois (L1B, #355, 30/10)** : `verify_isolation` ne rendait que le contournement. Une isolation posée sur le NSG du sous-réseau (une allow avant notre deny sur celui de la carte), une ancienne paire (noms fixes d'une version d'avant) contournée sur le NSG de la carte, nos règles retirées du sous-réseau : « contournée », les règles manquantes perdues — la réaffirmation, ne trouvant rien de manquant, ne les reposait ni ne les disait (L1 ; la machine, graine 42 à 500). Le contournement porte maintenant ce qui manque (`missing_rules`) : les règles que les placements de l'état enregistrent, absentes de la liste d'un NSG qui gouverne leur carte maintenant (une carte tenue par notre quarantaine exceptée) ; une liste ou un état illisible ne dit rien disparu. La réaffirmation les repose une fois (hors `human_only`) ou le dit, sur la carte de dérive, à côté de celle du contournement — comme I4C pour un blocage fusionné (`held_missing`, « Un blocage fusionné »). Code : `glorfindel/reassert_cards.py`, `providers/azure/verify.py` (`_recorded_gone`). Tests : `tests/unit/test_reassert.py`, `test_unreadable_state.py`.
- **Isolation JIT par NSG de quarantaine (lot L4, validé avec Jonathan le 2026-10-06)** : le temps de l'isolation, **chaque NIC porte le NSG de quarantaine de Glorfindel** (`nsg-glorfindel-quarantine-<région>`, tags `managed-by=glorfindel`, deux règles deny-all en 100, créé au premier besoin dans `isolation.quarantine_rg` de `glorfindel-config.yaml`, défaut : le RG de la VM ; `isolation.quarantine_nsg: false` ou `GLORFINDEL_QUARANTINE_NSG=0` pour revenir aux règles). Une NIC sans NSG le reçoit ; une NIC **avec** son NSG le reçoit **à la place** — le NSG client et ses règles restent intacts, et reviennent à la levée. Aucune règle client touchée, aucune préséance possible, isole aussi une NIC sans aucun NSG.
  - **Terraform — mesuré sur le banc (azurerm 4.81.0, pile jetable, 8 tests)** : échange ou accroche hors Terraform → `plan` sans changement, `apply` ne remet rien ; un `apply` qui modifie la NIC (tags) garde notre NSG ; le client qui **ajoute** une association en code pendant l'isolation → son `apply` échoue (`ImportAsExistsError`) ; remettre le NSG client → `plan` propre. **Reprennent la main** : le remplacement forcé de l'association (ou un changement de NSG dans son code, ForceNew) et un **redéploiement Bicep/ARM** de la NIC (même incrémental) → son NSG revient / le nôtre est retiré. Raison : la ressource NIC ne porte pas son NSG, et la lecture de l'association ne vérifie que la *présence* d'un NSG, sans comparer lequel.
  - **DNS et IMDS d'Azure (L17, mesuré le 07/10)** : un deny-all ne filtre pas 168.63.129.16 (DNS) ni 169.254.169.254 (IMDS) sans leurs service tags — une VM isolée résolvait encore les noms (tunnel DNS) et récupérait un jeton d'identité managée. Le NSG de quarantaine porte `glorfindel-quarantine-deny-dns` (110, `AzurePlatformDNS`) et `-deny-imds` (111, `AzurePlatformIMDS`), ajoutés aussi à un NSG existant. Mesuré : résolution et IMDS bloqués, **Run Command toujours fonctionnel** (WireServer non couvert par ces tags), tout revient à la levée. `isolation.forensic_sources` (adresse ou petit préfixe, validés — L20) → allow entrante TCP sur `isolation.forensic_ports` (22, 3389) en 90 avant le deny (Bastion, rebond d'investigation) ; la coupure n'épargne que ce que cet allow laisse entrer — une session TCP venue d'une source vers un port forensique de la VM (son port local) — toute autre session avec cet hôte est coupée (S8, 15/10). Le repli par règles ne peut pas refuser DNS/IMDS à une seule VM (mesuré, L20) : il le déclare — et depuis S7 (15/10), on le voit : puce orange « ⚠ DNS/IMDS » à côté d'ISOLATED (`/api/state` `platform_open`, `actions.platform_open_nics` : les cartes sans placement de quarantaine), ligne dans `glorfindel list`, note dans la notification d'une isolation autonome.
  - **L'original** est enregistré dans l'état ET, avant l'échange, en tag sur notre NSG (`glorfindel-orig-<hash de la NIC>` → id du NSG client ; pas sur la NIC : Terraform réécrit ses tags) → `release` et `reset --from-azure` le remettent même sans état local. La levée ne touche la NIC que si elle porte encore **notre** NSG. Pour juger si ce NSG d'origine est partagé, la NIC partie en quarantaine (ou laissée nue) compte parmi les siennes : comptées seules, les cartes attachées faisaient passer pour dédié un NSG resté à une autre VM, et `reset --from-azure` y supprimait l'ancienne isolation à noms fixes de cette VM (I4F, #235).
    - **À qui sont les noms fixes d'une ancienne version** (`glorfindel-isolation-deny-all[-out]`, et le nom de blocage sans VM `glorfindel-block-<ip>`) : à la VM du NSG, seulement si ce NSG ne gouverne qu'elle. Une carte d'une **autre** VM partie de ce NSG compte aussi (I4S, #239) : en quarantaine ou laissée nue, rattachée à ce NSG par notre tag `glorfindel-orig-<hash>` (sur un NSG de quarantaine `managed-by=glorfindel`), ou, le tag perdu, par l'état local de sa VM. Avant : l'ancienne isolation d'`api`, `api` en quarantaine, une nouvelle VM attachée seule au NSG d'`api` — son `reset --from-azure` (ou sa levée) supprimait les noms fixes d'`api` ; aucun flux ouvert (la quarantaine tient `api`), mais au retour de sa carte sur ce NSG hors de Glorfindel (redéploiement ARM/Bicep), la règle n'y était plus. Un tag périmé (carte supprimée depuis, ou rendue à un NSG hors de Glorfindel) ne rattache rien : la VM réellement seule reprend ses noms fixes. Le partage illisible — le NSG lui-même, ou la liste des NSG ou des cartes de l'abonnement (403, 429) : on ne sait pas, les noms fixes restent et le rapport le dit. Pour les noms d'isolation, `reset --from-azure` et la levée : « NSG … au partage illisible : isolation d'une ancienne version, VM inconnue », `swept_partial` / `release_partial`. Pour le nom de blocage simple, `unblock` : « … au partage illisible : blocage d'une ancienne version, VM inconnue) : laissée », `unblock_partial` — l'IP reste bloquée ; avant la relecture d'I4S, il répondait `not_found` en la laissant. Quand ce NSG est aussi celui du sous-réseau de la carte, le nom simple est aussi celui d'un blocage de périmètre : « blocage d'une ancienne version ou de périmètre » (ISU, #264). Limite : une carte dont plus rien ne dit l'original (tags et état perdus) ne rattache aucun NSG.
    - **Coût** : ces lectures (`network_security_groups.list_all`, et `network_interfaces.list_all` pour une carte nue) n'ont lieu que sur un NSG qui porte un nom fixe et ne gouverne qu'une carte — un héritage d'une ancienne version, rare. Là, chaque lecture des cartes d'une VM les fait : isolation, levée, reset, déblocage, mais aussi `verify_isolation` à chaque passe de la réaffirmation et l'accès aux NSG lu par la console. Gardé ainsi exprès : vérification et levée doivent lire à qui sont les noms fixes de la même façon, sinon `verify_release` compterait comme ceux de la VM des noms fixes que la levée laisse. Retirer l'ancienne règle (ou la reset de sa VM) supprime le coût.
    - **Hypothèse (SDK, non mesurée au banc)** : le `get` d'un NSG renvoie ses `security_rules` — le correctif s'y appuie pour voir un nom fixe. Sans ce champ, il deviendrait inerte (le comportement d'avant I4S, cas d'I4F toujours couvert), jamais dangereux.

  - **Ce qui fait foi pour l'original : l'état, sauf son « aucun » face à un tag qui nomme un NSG (I8S, #245, 28/10)**. Deux hôtes Glorfindel ont chacun leur état : l'hôte 1 isole une carte nue (« aucun »), le client lui donne ensuite un NSG X, l'hôte 2 l'isole (tag : X) — l'« aucun » de l'hôte 1 est périmé, le tag dit vrai. Désormais, quand l'état local dit « aucun » : un tag lisible qui nomme un NSG l'emporte, à la levée (carte en quarantaine ou laissée nue), dans `reset --from-azure` et dans `verify_release` ; les deux hôtes dans des groupes de quarantaine différents, le tag qui nomme un NSG l'emporte aussi sur un « aucun » trouvé d'abord dans un autre groupe (relecture 5.5) — un X dont le NSG n'existe plus fait alors échouer la levée, qui le dit, comme tout original supprimé ; pas de tag, ou notre NSG disparu : « aucun » tient ; un tag **illisible** (429) fait échouer la levée (`release_partial`, `swept_partial`) — jamais « aucun » au hasard, la levée effacerait ensuite le tag ; la carte n'est jamais remise nue sur cette erreur (le reset notait « aucun » avant de lire le tag : relecture 5.5). Une ré-isolation n'écrit plus l'« aucun » de l'état par-dessus un tag qu'elle n'a pas pu lire. Un original noté dans l'état (un NSG) l'emporte toujours sur le tag. Le déblocage lit maintenant l'original d'une carte nue comme la levée : celui de l'état, sinon notre tag sur le NSG de quarantaine de la région (l'« aucun » de l'état cède au tag qui nomme un NSG) ; une carte que l'état tient en quarantaine sans original, qu'aucun tag ne nomme (Q7) → `unblock_partial` (« carte sans NSG, ni l'état local ni le tag ne le disent »). Coût : pour une carte sans NSG propre dont l'état ne dit pas l'original, ce sont les lectures de la levée (le NSG de quarantaine de la région dans chaque groupe, puis `network_security_groups.list_all`), à chaque déblocage — **le cas courant** d'une VM seulement bloquée, jamais isolée, quand les NSG sont posés sur les subnets seulement. Une de ces lectures refusée (403 d'un rôle limité au groupe, 429) → `unblock_partial` (« NSG d'origine inconnu, déblocage non vérifié »), comme la levée d'une telle carte ; les règles trouvées ailleurs sont retirées quand même, l'entrée d'état du blocage, s'il y en a une, reste pour un nouvel essai. Option écartée (relecture d'U3F) : ne lister l'abonnement que si l'état tient la carte en quarantaine — l'état perdu et notre tag dans un groupe de quarantaine que la configuration ne nomme plus, le déblocage redirait `not_found` sur une règle restée (A0). **Cas marginal, côté fermé** (relecture d'I8S) : une carte laissée nue, deux groupes de quarantaine — `_bare_nic_original` cherche notre tag dans chacun, et un tag qui nomme un NSG l'emporte sur un « none » trouvé d'abord ; un X **périmé** dans l'un (un tag que la levée suivante, faite depuis l'autre groupe, n'a pas effacé) peut donc l'emporter sur un « none » juste dans l'autre ; la levée ou le reset remettent alors X (s'il existe encore — sinon elle échoue et dit comment en sortir, ci-dessous) : la carte reçoit un NSG de plus qu'elle n'en avait, jamais un de moins. Non corrigé : départager deux tags demanderait leur date, que Glorfindel n'écrit pas.

- `scope="vm"` (défaut, **autonome**) : scopé à l'IP de la VM sur NSG subnet (inbound src=attaquant/dst=IP_VM, outbound src=IP_VM/dst=attaquant, nom suffixé par VM) ou any sur NSG NIC → ne touche que cette VM. `scoped=True`.
- `scope="subnet"` (**opt-in délibéré opérateur**) : une règle `any` (attaquant↔*) sur le **NSG du subnet** (`_get_subnet_nsg`, nom partagé sans suffixe) → bloque l'IP pour TOUT le subnet (+ VMs futures). `scoped=False` → War Room ⚠ subnet-wide. Erreur claire si le subnet n'a pas de NSG.
- `scope="subnet", replace=True` (**promote VM→subnet**, commit `522f572`) : **create-then-delete** — pose d'abord la règle subnet-wide (la VM est alors couverte) puis supprime la règle VM redondante → **jamais de gap de protection** (si la pose subnet échoue, la règle VM reste intacte, pas de rollback nécessaire). État remplacé (1 entrée), outcome porte `promoted_from`.
- Recommandation : une seule règle `any` pour le subnet-wide (pas N règles scopées) — couvre les VMs futures, cycle de vie simple. La **modal de choix** (VM vs subnet) + passage de `scope` via `/api/action approve` + affordance « Extend to subnet » (`/api/action/block-promote`) = travail War Room.

- **Un blocage fusionné (RB1, #321, 29/10)** : un `block_perimeter` puis un `block` de la même VM (ou l'inverse) partagent une entrée d'état (`scoped: false`, la règle de périmètre et les placements de la VM). La vérification (`verify_block_ip`) la lit carte par carte : une carte dont les règles propres manquent (supprimées, retournées en allow) est encore bloquée là où une règle de périmètre de l'IP la couvre — celle de l'entrée, ou celle d'une autre VM du subnet (une seule règle pour tout le subnet, nommée par l'IP seule : trouvé par la machine sur le premier correctif) — sur un NSG qui la gouverne maintenant, ses deux règles présentes et entières, aucune allow avant elles qui laisse passer le port de la menace (`held_by_perimeter`, `verified: true` avec `held_missing`) ; une carte qu'elle ne couvre pas (sur un autre subnet : le périmètre est posé sur le subnet de la carte primaire) est ouverte (`open_nics`) ; une règle de périmètre illisible laisse la carte inconnue (`perimeter_unread`), jamais « bloquée » ni « ouverte ». La paire de périmètre elle-même est vérifiée : supprimée, elle disparaissait en silence pour les autres VM du subnet. Et derrière un contournement (I4C, #344) : les règles propres de la VM présentes mais contournées (une allow du client avant elles), la paire levée par le déblocage d'une voisine n'était pas dite — la vérification ne rendait que `shadowed_by` ; elle rend aussi ce qui manque (`held_missing`), et la réaffirmation le repose ou le dit. La réaffirmation repose **les deux** (le périmètre, puis les placements de la VM), relit Azure, et ne dit « reposé une fois » que d'un blocage entier ; sinon sa carte dit ce qui ne tient toujours pas (`partial`, une carte par épisode). Sa carte ne dit jamais « l'IP n'est plus bloquée » d'une IP que le périmètre (ou la quarantaine) coupe encore : « l'IP reste bloquée sur <carte> par la règle de périmètre <nom> ». Avant : seule la règle de périmètre était réécrite ; sur un seul subnet, la passe suivante disait l'IP débloquée (faux, du côté prudent) ; sur deux subnets, « reposé » alors que la seconde carte restait ouverte. Code : `providers/azure/perimeter.py`, `unblock.py`, `reassert.py`.

- **Une règle du blocage retournée, sur une adresse reprise (I4A, #328, 29/10)** : un blocage écrit de nouveau (un second `block`, la réaffirmation hors `human_only`) réécrivait ses règles par leur nom. L'une d'elles passée en allow par un tiers, visant encore une adresse qui n'est plus celle de la carte (son IP a changé, et Azure a donné l'ancienne à une nouvelle VM), laissait l'attaquant joindre cette autre VM : réécrite pour la nouvelle adresse, l'allow disparaissait — l'opération sur une VM changeait les flux d'une autre (I4). Une règle de la première paire qui n'a pas pu être retirée est dite (`drop_failed`, dans `left_rules` et la carte) : si elle vise l'ancienne adresse, elle coupe la VM qui l'a reçue. Sinon notre deny est réécrit comme avant : il ne rend que ce qu'il coupait. L'ancienne adresse à personne : réécrite comme avant (I7S). « Personne » veut dire aucune carte de VM : la liste des cartes ne donne pas celles d'un VMSS, une instance de VMSS qui tient l'adresse n'est pas vue (angle mort ancien, le même que `private_ip_owners`). Le blocage le dit (`left_rules`, sa note avec la commande qui la retire) et le garde dans son placement (`left`) ; la réaffirmation suivante le dit sur une carte (`rule_left`, action `review_left_rule`), une fois par ensemble de règles (`left_said`), jamais d'écriture. Les deux paires prises ainsi : rien n'est écrit sur cette carte, le blocage échoue sur elle et le dit (partiel si une autre carte est déjà couverte). Coût : la liste des cartes de l'abonnement, une fois par blocage, seulement quand une allow à notre nom vise une autre adresse. - **Le déblocage, le reset, la levée et l'isolation, sur une adresse reprise (I4B, #333, 30/10)** : ils retiraient (ou réécrivaient) une règle à l'empreinte de la carte quoi qu'elle soit devenue (`_nic_owns`), y compris l'allow retournée qu'I4A laisse : la VM qui a repris l'ancienne adresse perdait les flux qu'elle lui donnait — et une isolation réécrite (à la main ou par la réaffirmation) quittait l'ancienne adresse où une de nos règles retournée attendait derrière son refus : cette VM s'ouvrait à l'attaquant (I4, I5). L'isolation réécrite fait comme le blocage d'I4A : elle lit sa paire en place, laisse ce que la garde garde (`left_rules`, `left_note` ; la carte de la réaffirmation le dit), s'écrit sous le **second nom** de la carte (`glorfindel-iso-<vm>-<carte>-b-<empreinte>`, lu par la vérification, la levée et le reset comme le premier) et retire l'autre paire, à nous et ne visant aucune autre VM ; les deux paires prises, rien n'est écrit sur cette carte (isolation partielle). La garde du blocage lit aussi toute règle retournée des nôtres (une isolation, une autre carte) sur un NSG qui gouverne le détenteur de l'adresse (`_waits_for`), plus seulement celles du blocage de la carte ; illisibles : le refus reste (le garder n'ouvre rien). Et une carte sans NSG à elle que rien n'enregistre (son NSG retiré par quelqu'un, l'entrée du blocage perdue) : le déblocage cherche son blocage, à son empreinte, sur tous les NSG de l'abonnement (`_unplaced_blocks`) — il disait `not_found`, le blocage resté sur le NSG que la carte portait (la CI macOS, graine au hasard à 500). L'aperçu de `glorfindel reset --from-azure` demande la garde aussi : il dit « gardée » avant la confirmation (relecture). Un refus d'isolation sur toutes les adresses (`*` : le refus total d'une ancienne version, ou le nôtre sur un NSG qui ne gouvernait que la VM) coupe toutes les cartes que son NSG gouverne : depuis I4C (#344), la levée (le chemin de l'état d'une ancienne version compris, qui ne demandait rien) et le reset le demandent à la garde, qui compte ces cartes (`turned._cuts_all`) — une VM qui a reçu ce NSG et une ancienne adresse depuis, une de nos règles retournée l'attendant derrière : il reste, dit (`release_partial`, `swept_partial`). ## Où vit le code Azure (A1, MC0, 26/10)

Tout ce que Glorfindel fait sur Azure vit dans `glorfindel/providers/azure/`, le seul endroit de
`glorfindel/` qui importe le SDK Azure ; `tests/unit/test_provider_boundary.py` (étape « Provider
boundary » de la CI) échoue sinon. L'ancien `glorfindel/actions.py` (4 394 lignes) y est découpé
sans changement de texte, un module par préoccupation, aucun au-delà de 430 lignes :

| Module | Ce qu'il porte |
|---|---|
| `connector.py` | `AzureConnector` (un mixin par préoccupation), la garde d'abonnement, le verrou de VM sur les écritures |

| `quarantine.py` | le NSG de quarantaine : pose, NSG d'origine (état et tag), contenu attendu |
| `isolation.py`, `release.py`, `verify.py` | isoler (quarantaine, sinon règles), lever, vérifier |
| `blocks.py`, `verify_block.py`, `unblock.py` | bloquer une IP, vérifier, débloquer (`verify_block.py` sorti d'`unblock.py`, I4B) |
| `perimeter.py` | le blocage de périmètre d'une entrée fusionnée : où il tient une carte, lequel une autre VM enregistre (RB1) |

## Pitfalls opérateur

`backup_agent_check` retourne toujours `[]` sur les Linux VMs — `\\Process(*)\\IO Write Bytes/sec` est un counter Windows-only, Linux AMA ne le collecte pas. Idem pour `top_write_processes` (même counter). **C'est le comportement voulu** : résultats vides → le LLM ne peut pas exclure le ransomware → escalade forcée. L'alternative (`az backup job list` via RunCommand) ajouterait latence 15-30s + dépendance AZ CLI in-guest pour un résultat qui rendrait le produit trop confiant sur des données incomplètes.

`annatar run` fait un preflight check automatique (VM running + pas de règles `glorfindel-isolation-*`). Si ça échoue, le run s'arrête avec la commande exacte à lancer. `--skip-preflight` pour bypasser.

Après un `restore_from_backup`, le backup suivant est un **full backup** (~40min–4h selon Azure). Aucune API ne permet de prédire la durée. Le `glorfindel snapshot` du setup T1486 suivant peut donc être long. À anticiper avant les sessions de test.

```bash
# Si preflight échoue — commandes de fix
glorfindel list                           # voir isolations + IPs bloquées
glorfindel reset <resource_id> --yes     # reset complet

# Vérification NSG directe si besoin
az network nsg rule list -g rg-celebrimbor --nsg-name nsg-celebrimbor -o table
```
